# ADR-007：CI 平台採用 GitHub Actions

- **狀態**：已接受
- **日期**：2026-08-16
- **決定者**：使用者裁決
- **對應**：`02-architecture.md` D7、`04-agent-execution-dsh.md` §4

## 脈絡

工廠需要一個執行引擎來承載 Control Plane 的邏輯：接收觸發、執行計分、呼叫 DSH、判讀結果、施加閘門。

同時，`00-source-summary.md` §3 Phase 1 Step 1 明示了一項**前提條件**：

> 傳統（非 AI）自動化實踐，例如持續整合（含單元測試自動化）、靜態程式碼分析、自動化生產部署，**應被視為引入 AI 進行更進階使用案例之前的基本前提**。

## 決策

**以 GitHub Actions 作為唯一的 CI/CD 執行平台與工廠的 Control Plane 執行引擎。**

## 後果

### 正面
- 與 ADR-001（GitHub 為唯一事實來源）自然一致，不引入第三方系統與額外的身分整合。
- `workflow_dispatch` 提供 Backstage Template 的觸發端點（`03` §3.2）。
- run 歷程即稽核紀錄，無須另建。
- **每次 run 為全新、用完即棄的環境**——免費提供 `00` §4 支柱三要求的隔離基礎設施，並自動滿足 `01` §3 消除清單 E1（消除手動開環境票）。
- 不同工作項的 run 天然平行，支援 `00` §3 Phase 2 要求的非同步平行化。

### 負面
- runner 為 Linux（`ubuntu-latest`），與本機 macOS 開發環境不同；**DSH 沙箱（landlock 為 Linux 機制）的跨平台行為需驗證**（Q02-2/Q04-3）。
- 受 GitHub Actions 的並行數與時間上限約束，限制平行化的可達程度。
- **GitHub-hosted runner 的出向網路預設不受限**（Q05-1，已記錄為殘餘風險）。

### 中性
- 需以 `concurrency` 群組避免同一 Issue 被重複觸發（`04` §4.3）。

## 重要區分：平台就緒 ≠ 前提就緒

> 採用 GitHub Actions 只確立了**載體**，不代表 `00` §3 Phase 1 要求的前提已滿足。

仍須確認目標 repo **實際具備**：
- 可自動執行的測試，且涵蓋核心路徑；
- 靜態分析與 lint；
- 自動化部署。

此驗證列為 `09-roadmap.md` **第 0 期的出場條件**（Q02-6）。

**若目標 repo 的測試覆蓋薄弱到無法信任 CI 綠燈，且團隊無意補強——應停止整個工廠專案**（`09` 第 0 期放棄條件）。理由：工廠的安全性完全建立在「CI 綠燈代表沒有明顯破壞」這個假設上。假設不成立時，工廠只是一台高速產生未驗證變更的機器。

## 替代方案

### A. 獨立 CI 系統（Jenkins、CircleCI、GitLab CI）
**未採用的理由**：需額外的身分整合、webhook 設定與維運人力；且稽核紀錄與 GitHub 分離，違背 ADR-001 的單一事實來源原則。對小團隊而言成本不成比例。

### B. self-hosted runner
**未採用的理由（第一階段）**：可解決出向網路限制（Q05-1）與資源上限，但需要維運基礎設施。第一階段選擇 GitHub-hosted 並明確揭露殘餘風險；**保留未來升級路徑**——若開始處理敏感資料，應改用 self-hosted + 出向白名單。

### C. 本機執行（開發者手動觸發）
**未採用的理由**：無法無人化、無稽核紀錄、環境不一致，且使 agent 在開發者機器上以其個人權限執行——這正是 ADR-006 要避免的身分混淆。
