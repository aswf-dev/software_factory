# ADR-005：自主性上限設為 on-the-loop 低風險類別

- **狀態**：已接受
- **日期**：2026-08-16
- **決定者**：平台架構 / 技術主管
- **對應**：`02-architecture.md` D5、`06-human-oversight-policy.md`、`09-roadmap.md` 第 3 期

## 脈絡

`00-source-summary.md` §3 Phase 3 描述了自主軟體交付的願景：vibe coding 的 prompt-to-app、自主工作負載最佳化、人類工作從命令式轉向宣告式。

但同一份研究也提出三項限制：

1. **§3 Phase 2**：現階段技術成熟度**無法保證一致性、準確性或可預測性**，human-in-the-loop 監督為**強制**。
2. **§6**：監督強度應依業務關鍵性、風險輪廓、架構複雜度決定。
3. **§7**：技能退化警示——AI 依賴侵蝕獨立判斷力，工具失效時反而損害生產力。

## 決策

**本專案的自主性上限明確設定為「human on the loop 且限定低風險類別」。**

具體而言，agent 自動合併僅限於同時滿足：
- `06` 三軸計分為 0–1 分；
- 屬於 `00` §6 明列的 on-the-loop 類別（測試、文件、相依更新、程式碼異味重構等）；
- `06` §4.1 的全部附加條件。

### 明確排除

- ❌ 生產環境自動修復
- ❌ 高風險類別（授權、金流、敏感資料、架構變更）的自主執行
- ❌ 跨組織 agent 生態系（`00` §5 的最高層級）
- ❌ vibe coding 式全自主流程

## 後果

### 正面
- 風險有界：最壞情況下，agent 自動合併的錯誤僅限於低風險類別。
- 核心工程能力持續由人行使，直接因應技能退化警示。
- 符合來源研究對現階段技術成熟度的判斷。

### 負面
- **無法達到 `00` §9 預測的完整生產力增益**（2028 年 30%–50%）。這是有意識的取捨。
- 高風險工作的速度不會顯著改善。

### 中性
- 上限**可依數據放寬**，但程序嚴格（`06` §7.2、`09` 第 3 期進入條件）。

## 放寬與收緊的不對稱設計

| 方向 | 條件 |
|---|---|
| **放寬** | 需要數據：該類別缺陷逃逸率為 0，樣本 ≥ 50，且經 platform-team 審查 |
| **收緊** | 只需要一次事故：任一自動合併類別出現缺陷逃逸，**立即收回** |

> **這種不對稱是刻意的。** 放寬自主性是不可逆的信任讓渡——收回時，團隊往往已經失去原本的審查習慣。使放寬困難、收緊容易，是對這種不可逆性的防護。

## 替代方案

### A. 追求完全自主（Phase 3 完整願景）
**未採用的理由**：來源研究自己就明示現階段技術無法保證可預測性。在小團隊、無專職安全人力的條件下追求完全自主，是把研究的**願景**當成**現狀**。

### B. 完全不開放自動合併
**未採用的理由**：過度保守。`00` §6 明列的低風險類別（產生測試、文件、相依更新）確實適合 on-the-loop；全部人工審查會讓工廠的價值大打折扣，且浪費人類注意力在最不需要判斷的地方。

### C. 依 repo 而非依任務類型決定自主性
**未採用的理由**：同一 repo 中不同變更的風險差異極大——內部工具也可能有授權邏輯。`06` 的三軸計分能區分到變更層級，粒度更恰當。

## 值得記住的張力

`05` §7.1 已指出：**嚴謹審查與提升速度之間的張力無法用工具消除**。

本 ADR 的立場是——**承認這個上限，比假裝它不存在要安全得多**。工廠可以提高產出，但審查容量是人類的、有限的、不可自動擴張的。
