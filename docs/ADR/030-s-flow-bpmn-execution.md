# ADR-030：S 專案流程改由 BPMN 引擎執行——狀態以 D1 事件日誌為唯一事實

- **狀態**：已接受（2026-11-01，使用者經 grilling 逐題裁決 Q1–Q25 並確認共識摘要；實作依 §9 驗收）
- **日期**：2026-11-01
- **決定者**：使用者
- **修訂**：`ADR-015`（Worker bundle 自訂門檻 1 MiB → 2 MiB）、`ADR-028` §4（執行平面先以 D1 落地，DO 的搬遷條件見 §7）
- **對應**：`ADR-027`（BPMN 編排）、`ADR-028`（BPMN 執行核心）、`ADR-029`（形式化驗證服務，本 ADR 沿用它的 D1 journal 模式）、`ADR-001`（GitHub 為事實來源）、`ADR-006`（GitHub App 身分）、`ADR-023`／`ADR-024`（`process.yaml` 與快照路徑，本 ADR 只接管 S 模板）、`ADR-025`（租戶模板）

## 脈絡

`factory/S`（小型專案導入流程：P0 納管 → P1 量測盤點 → P2 文件與規則 → P3 測試與缺陷 → P4 維護）目前的「執行」方式與 `ADR-027` 的目標不一致：

- **沒有任何引擎在執行 S。** 流程頁的狀態是**推算**出來的：機制端每天排程（`factory-snapshot.yml`）讀 GitHub Issue（內文的 `> 流程步驟：S10`、標籤、HG 簽核留言），以 `factory-graph` 產生快照發佈，`aswf.dev` 只讀不快照（`ADR-001`／`ADR-023`）。新工作項由 `factory-next` 產生「建議下一步」，人按下送出才走既有入口（`ADR-024`）。
- **S 有兩份各自維護的定義而且已經不一致。** 拓撲 UI 用 `src/lib/process/fixtures/definitions/S.json`；BPMN 產生器用 `src/lib/bpmn/templates/source/S.yaml`。S10 在 JSON 是「三選一分支」，在 YAML 是 `alternatives` 清單；S6 的範圍與 HG 位置也不同。
- **S/M/L 的 BPMN 模板是暫定版。** `src/lib/bpmn/templates/README.md` 明文寫著：`conditional: true` 與 `required: false` 的步驟被簡化為一律執行、`alternatives` 被簡化成只取第一個，因此「不得用它啟動真實實例」。
- **推算是隔天的。** 快照一天一次，而且 2026-10-22 之後因排程發佈條件的 bug（`inputs.publish != false` 在排程觸發時恆為 false）整週沒有更新，直到 2026-11-01 才修。
- **`factory/S` 目前沒有任何真實系統在用**（只有合成樣本 `inventory-service`）。真實系統用的是自訂模板（`tradingbot-tw/saga-pattern`、`agent-playground/restate-cloudflare-workers-poc`），它們繼續走快照路徑。

`ADR-027` 已經決定「流程位置由執行平面權威」，`ADR-028` 決定技術選型（bpmnkit）並規劃 Durable Object，`ADR-029` 已把「D1 journal＋每個請求重播」在正式環境跑通四階段。本 ADR 決定：**S 也走同一條路，先以 D1 落地。**

## 決策

### 1. 範圍（Q1、Q25）

- **只做標準模板 `factory/S`。** M／L 與租戶自訂模板維持現狀（快照＋React Flow），顯示也在之後再統一。
- 但實作寫成**通用的流程執行層與圖形元件**：不明寫死 S，M／L 與自訂模板之後可依序接上。

### 2. 定義來源（Q4）

- **`S.yaml` 是唯一來源**，由產生器轉成 BPMN。`S.json` 廢除，`/scoreboard/process/flows/S` 改由 BPMN 產生圖形。
- 產生器補強（`src/lib/bpmn/generate.ts`）：
  - **條件式步驟**（S9 `conditional: true`）：來源清單為空時自動略過（略過分支要真的建模，不是只留屬性）。
  - **多選一**（S10、S11 `alternatives`）：產生人工選擇步驟，人選定後才走對應分支；**引擎不自行挑選**。
  - **選擇性步驟**（S11 `required: false`）：可略過、可重複。
- README 的「暫定版」標記在 V1 完成後移除；在那之前**不得**啟動真實實例。

### 3. 流程語意（Q10、Q11、Q15）

| 步驟 | 執行方式 |
|---|---|
| S0 開導入追蹤 Issue | **自動**（流程直接開，營運者不必操作） |
| S1 安裝 App、建分支 | **人工確認＋自動檢查**（頁面顯示 App 是否已安裝、分支是否存在；分支可由按鈕建立） |
| S3 裁定三軸（HG1） | **人工**：頁面列出 S2 納管提案結果，營運者填三軸裁定並確認＝簽 HG1 |
| S7 核心業務規則（HG4） | **人工**：貼上文件位置並確認＝簽 HG4 |
| S9 修缺陷 | 缺陷清單空 → 自動略過 |
| S10 驗證閘門 | S10 前**人工表單逐模組選擇** Quint 規格／性質測試稽核／人工豁免；豁免直接進 HG5 |
| S11 維護 | **人工表單**：略過或三種工單之一，可重複，直到按「結束流程」 |
| 模組清單 | **P3 前新增人工步驟「確認模組清單」**：預填 S5 盤點結果，營運者增刪後才進 P3（Q11=b） |

- **工單完成判定沿用現行規則**：Issue 關閉／貼 `stage/done`／PR 合併（與 `factory-graph` 現在的判定一致），兩邊定義不得分歧。
- **N-version 不變**：BPMN 只負責開 Issue 與派工，雙變體、挑選、合併照機制端現有規則（Q16=a）。

### 4. 啟動權限與實例（Q5、Q14）

- **只有營運者能啟動**：`/scoreboard` 上按「開始」（Cloudflare Access 保護）。對外開放（比照 `ADR-029` 的 GitHub 登入）列為後續。
- **同一 repo 同時只能有一個進行中的實例**；完成或取消後才能再開。

### 5. 儲存與推進（Q7、Q12）

- **事件日誌存 D1**，沿用 `ADR-029` 驗證過的形狀：實例表、journal（`實例 id＋seq` 樂觀並行）、effect 認領表。**verify 的表不動**，新增通用表。
- **每一次請求依 journal 重播 runtime**（與 verify 相同）；Worker 無狀態。
- **推進來源**：
  - **GitHub webhook 為主**：PR 合併／Issue 關閉／標籤變更時推進。
  - **排程輪詢補漏**：每 5 分鐘掃描進行中的實例，補上漏掉的 webhook，並推進「沒有任何人開頁面」時的下一步。
- **不引入 Durable Object**（本階段）。搬遷門檻見 §7。

### 6. 簽核與介面（Q6、Q17、Q18）

- **所有人工步驟與 HG 閘門都在 `aswf.dev` 上按按鈕**，journal 是唯一事實；GitHub Issue 只留稽核留言，不回頭驅動流程。
- **工單失敗**（`needs-human`、逾時、run 失敗）：流程**不自動重試**；狀態頁顯示哪張工單卡住與原因，提供「重新派工」「人工標記完成」「取消整個實例」三個動作。
- **狀態頁顯示**：
  - 上方一列 **P0–P4 階段總覽**（完成／進行中／卡在閘門／未開始），下方**展開目前階段**的 BPMN 圖，其他階段點擊展開。
  - 多模組步驟顯示「3／5 模組完成」，點進去列每個模組。
  - 圖形**伺服器端產生 SVG**（沿用 `ADR-029` 的做法，不引入前端繪圖套件），手機可橫向捲動。

### 7. 與既有機制、程式碼的關係（Q13、Q19）

- **用 BPMN 跑的系統不寫 `process.yaml`**，因此不會被快照／`factory-next-actions` 處理；舊機制繼續服務現有的自訂模板系統。一個系統只由一套機制指揮。
- **新寫通用執行層給 S 用，verify 先不動**（Q19=b）。短期會有兩套相似的程式；合併列為後續（§10）。
- **Durable Object 搬遷門檻**（寫進此處供未來判斷）：任一條成立就重新評估 `ADR-028` 的 DO 平面——
  - 單一實例 journal 超過 300 筆，或每個請求重播 CPU 超過 50 ms；
  - 需要即時推播（WebSocket）而非輪詢；
  - 排程輪詢的成本或延遲成為瓶頸。

### 8. 容量（Q8）

- Worker bundle 自訂門檻自 **1 MiB 調高至 2 MiB**（壓縮後），修訂 `ADR-015`。理由：S 的 BPMN（3.0 KiB gz）＋通用執行層＋頁面超出原本 2.6 KiB 的餘裕；2 MiB 仍保留到 Cloudflare 免費方案 3 MiB 上限的餘裕，付費方案為 10 MiB。

### 9. 里程碑與驗收

四個里程碑，各自獨立 PR 與驗收：

| # | 內容 |
|---|---|
| **V1** | 本 ADR ＋ 產生器補強（略過分支、多選一、模組確認步驟），S 的 BPMN 從暫定版升為可執行版 |
| **V2** | 通用執行層：D1 表（實例／journal／effect 認領）、runtime 服務、webhook 推進、排程推進、bundle 門檻調整 |
| **V3** | 頁面：BPMN 圖元件（階段總覽＋展開）、營運者啟動頁、人工步驟與 HG 簽核頁、流程頁換成 BPMN 圖 |
| **V4** | 在 `agent-playground/pottery` 從 P0 跑到 P4，產出驗收報告 |

驗收標準（比照 `ADR-029` §9）：

1. 在 `agent-playground/pottery` 完整跑完 P0→P4：開追蹤 Issue、納管、量測盤點、文件、規則、補測試、驗證閘門、維護。
2. 四個人工步驟與 HG1–HG6 都在 `aswf.dev` 上完成，GitHub 留下稽核紀錄。
3. 執行中途重啟 Worker 後，重播 journal 得到相同狀態，且**副作用不重複**（不重複開 Issue、不重複派工）。
4. webhook 漏掉時排程能補上；工單完成後流程自動推進。
5. 工單失敗時流程停在 needs-human，三個動作（重新派工／人工完成／取消）都可用。
6. 用 BPMN 跑的系統不出現在舊機制的 `next-actions`／快照中。
7. Worker bundle 在 2 MiB 門檻內。

## 考慮過的其他選項

- **只把 S 畫成 BPMN 圖（不改執行）**：改動最小，但狀態仍要靠隔天的快照推算，且無法解決「沒有引擎執行」的根本問題，等於把問題延後。（使用者裁決 Q2：要做真正的 BPMN 執行。）
- **沿用 Durable Object（`ADR-028` §4）**：隔離性與即時性最好，但要先建 DO 基礎設施（M2 未完成），且現階段沒有即時推播需求；`ADR-029` 已證明 D1 足以支撐。（Q7：先 D1，門檻見 §7。）
- **重構 verify 的程式成為共用層**：程式最乾淨，但會動到已在正式環境驗收過的 verify，需重跑全部回歸測試。（Q19：先另寫，之後再合併。）
- **手寫 `factory.S.v2.bpmn`**：可精確控制語意，但 M／L 與租戶模板仍需產生器，等於維護兩套。（Q4：修產生器。）

## 風險

| 風險 | 處理 |
|---|---|
| journal 隨模組數變長，重播成本上升 | §7 的搬遷門檻；實際量測寫進 V2 驗收 |
| 短期有兩套相似的執行層（verify 與通用層） | §10 合併待辦 |
| 產生器改動影響 M／L 的既有產出 | `test/bpmn/generate.test.ts` 與黃金日誌擋住；M／L 的模板在 V1 一併重新產生但不改變語意 |
| 舊機制與新機制對同一系統有兩套判定 | §7 第一條：用 BPMN 的系統不寫 `process.yaml` |
| 驗收 repo（`pottery`）需要 GitHub App 已安裝且有 Issues | S1 步驟會自動檢查並顯示結果；驗收前先確認 |

## 後續（不在本次範圍）

- verify 的執行層與通用層合併。
- M／L 與租戶自訂模板轉 BPMN（自訂模板目前只有 YAML，需新的轉換規則）。
- 對外開放（GitHub 登入）啟動 S 流程。
- 依 §7 門檻評估搬遷到 Durable Object。
- `ADR-023`／`ADR-024` 的 `process.yaml` 退場（`ADR-027` §11 原訂於 PoC 驗收後刪除）。
