# ADR-024：流程的「執行」語意——UI 產生待開工作項清單，人按下送出

- **狀態**：已接受
- **已被取代**：`ADR-027` §3／§6（已接受，2026-10-26）——「執行」改為由流程推進、人按送出後派工；§5「不新增隱藏標記」改為 Issue body 加 `factory:bpmn` 標記。
- **日期**：2026-10-18
- **決定者**：平台架構（使用者裁決：執行語意選 ii）
- **對應**：`ADR-023`（流程以 `process.yaml` 描述、拓撲 UI）、`ADR-022`（不自動派工下游，Q29-A）、`docs/29` §1.1 前提 2 與 §8（HG0）、`docs/31` §1（每張單由人開立）、`docs/24` §2.1（CI 無人確認＝拒絕）、`docs/10`（`Q-ORCH-3`）

## 脈絡

`ADR-023` 把流程的**呈現**定案了（`process.yaml` ＋ React Flow 拓撲 UI），並在 §4 明文把「派工、簽核」劃在 v1 之外。但後續需求追加了一句：**「存檔後，進行執行」**。

「執行」在工廠裡不是一個動作，而是一個**權限問題**。既有的三條硬規則把它夾得很緊：

1. `docs/29` §1.1 前提 2 ＋ HG0：**每一張工作項都由人類開立並送出**；agent 報告的「建議下一步」不會自動變成工作項。
2. `ADR-022` Q29-A：明文**不自動派工下游**；完成時只留言通知，派工由人按。
3. `docs/24` §2.1：CI 無人可確認 → **等同拒絕**（fail-closed），不是等待。

因此「存檔即派工」不是一個 UI 功能，而是**推翻上述三條**的治理變更。本 ADR 選擇不推翻它們，並定義一個不與之衝突的「執行」語意。

## 決策

### 1. 「執行」＝產生待開工作項清單（next actions），不建立任何 GitHub 物件

- UI 依 **S/M/L 模板**（`docs/29` §9.1–9.3 的機器可讀版）＋ 目前狀態（模組就緒度、已簽 HG、未完成前置），算出「**下一步該開哪些單**」的清單。
- 清單是**純計算結果**：不建 Issue、不貼 label、不觸發 workflow。
- 每一項必須帶：目標（模組或系統）、工作項類型、模板步驟、理由（缺哪個閘門／哪個前置）、以及預填的 PRD 四段。
- **系統層步驟**（`per: system|repo` 的 work-item，例如 P0 的分析、P1 的規格）也會出現在清單中：scope 是系統本身、**一次只建議一筆**（依模板順序），避免一次湧出多張系統層單；系統層人類步驟不開工單，閘門未簽時建議簽核。模組層建議不受系統層步驟阻塞（P2–P4 仍各自推進，`docs/29` §6）。

### 2. 人按下送出 → 走既有入口，不新增派工入口

- 送出＝由人按下，走**既有的** Backstage「開立 Factory 工作項」表單或 GitHub issue form，再經 `factory/approved` → `factory-issue-check` → `factory-run`。
- **不得**由 UI 直接呼叫 `factory-run`、直接貼 `factory/approved`、或繞過 `factory-issue-check` 的格式檢查。
- 這一條把 HG0 的語意原樣保留：**「送出即核准」仍然是人按下的那一下**。

### 3. `process.yaml` 的存檔一律走 PR，由人審

- UI 不直接寫入任何 repo；產生存量變更（模組、閘門、順序）→ 產生 `process.yaml` 的 diff → **開 PR**。
- 理由不只是治理：Scoreboard 目前的 GitHub App 權限沒有 `pull_requests`，且 `src/pages/api/**` 在 Scoreboard 屬 H7。寫入行為必須是一個獨立、可審、可回滾的動作。
- `process.yaml` 的變更因此**一定留下 review 紀錄**，與 `docs/05` 的「變更留下 diff」同一精神。

### 4. 清單是 advisory，不得取代任何機械判定

- 「待開工作項清單」**不得**成為 `factory-stage prereqs` 的替代品。派工前的唯一機械檢查仍是 `factory-run.yml` 的 `factory-stage prereqs`（`ADR-022`）。
- 清單算錯的後果只能是「少開或多開一張單」，**不能是「跳過一個前置」**。
- 與 OpenRig 的教訓一致：advisory（`rig proof`、`artifact-pool-ready`）一旦被當成 gate，就會產生靜默失效。

### 5. 冪等與重算

- 清單以 `(system, module 或「系統層」, template-step, source-rev)` 為鍵；同一輸入重算結果必須一致。
- 已開立且對應到該鍵的工作項不得重複出現在清單中；判定依據是 Issue body 的既有欄位（`### 任務類型`、`### 目標模組 / 檔案`），**不新增隱藏標記**。

## 後果

### 正面

- 「模板 → 調整 → 存檔 → 執行」有了完整語意，且**沒有推翻任何既有治理規則**：HG0 不變、`ADR-022` 不變、`docs/24` §2.1 不變。
- 「執行」的價值落在**人少想一件事**（清單由模板與狀態算出），而不是「機器替人按下」。
- 失敗模式明確：清單錯了就是多開／少開一張單，人看得到、改得動。

### 負面

- 人仍要逐張按下送出——對大型專案（每次 P1 可能十幾張 analysis 單）是實際的操作成本。
- 清單品質完全依賴 `factory-graph` 的正確性；若 HG 狀態或就緒度讀錯，清單會系統性偏誤（且看起來很有說服力）。
- 「一鍵批次」被排除，會有人要求它（見 `Q-ORCH-3`）。

### 中性

- UI 的「執行」按鈕本質上是**導頁／預填**，不持有任何憑證或派工能力。
- `process.yaml` 的變更頻率預計很低（模板固定、模組邊界少動），PR 流程的成本可接受。

## 替代方案

| 方案 | 為何未採用 |
|---|---|
| **(i) 只顯示、不產生清單** | 等於讓「存檔後執行」變成一句空話：人看完圖仍要自己想「下一步開哪張單」，正是 `docs/31` §0 要解決的缺口。 |
| **(iii) 存檔即派工（UI 直接觸發 `factory-run`）** | 直接推翻 `docs/29` §1.1 前提 2、HG0、`ADR-022` Q29-A 與 `docs/24` §2.1；且會讓 UI 持有派工憑證，新增一個 H1 級入口。要走到這一步必須另立 ADR 並逐一裁決上述四條。 |
| **UI 直接建立 Issue（不經人按）** | 與 (iii) 同樣的問題；且 Issue 建立後仍需 `factory/approved` 才會派工，等於多一層無效的中間狀態。 |
| **在 GitHub 上（Action／bot）產生清單** | 清單需要模板與模組狀態的互動式調整，放在 UI 才看得到；且會讓「誰觸發」變得模糊。 |
