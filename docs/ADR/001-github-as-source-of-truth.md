# ADR-001：GitHub 為唯一事實來源，Backstage 為入口

- **狀態**：已接受
- **日期**：2026-08-16
- **決定者**：平台架構
- **對應**：`02-architecture.md` D1

## 脈絡

工廠需要記錄工作項狀態、執行紀錄、審查閘門與稽核歷程。可能的存放位置有三：Backstage 自建資料模型、獨立的工作流資料庫、或直接使用 GitHub 既有實體。

限制條件：
- 團隊規模小（3–10 人），維運人力有限。
- 使用者已確認以 GitHub 為既有版控平台。
- `00-source-summary.md` §3 Phase 1 Step 3 要求建立 IDP 提供「paved roads」，但未規定狀態必須存於 IDP。

## 決策

**工作項狀態、執行紀錄、審查閘門、稽核歷程一律存放於 GitHub**（Issue / PR / Actions run）。

**Backstage 不儲存工廠狀態**，只負責展示與觸發。Backstage 的 Catalog 是 GitHub 資料的投影。

## 後果

### 正面
- 不需維運額外的工作流資料庫。
- 消除雙寫造成的不一致。
- GitHub 已提供狀態機、權限模型、稽核歷程與通知，無須重建。
- **Backstage 掉線時工廠仍可運作**——人類可直接在 GitHub 建 Issue、手動觸發 workflow（`02` §6 的降級路徑）。
- 大幅降低更換 IDP 的成本。

### 負面
- Catalog 需容忍最終一致性（探索有延遲）。
- 受 GitHub API 限流約束。
- 工廠與 GitHub 深度耦合；若未來更換版控平台，Control Plane 需重做。

### 中性
- 需要明確的架構違規判準：**任何「只存在於 Backstage 而 GitHub 沒有」的工廠狀態都是違規**，實作審查以此為檢查點。

## 替代方案

### A. Backstage 自建工作流資料模型
**未採用的理由**：造成雙寫與不一致；且使 Backstage 成為單點故障——它一掉線，工廠即停擺。對小團隊而言，維運成本與風險都不成比例。

### B. 獨立的工作流引擎（如 Temporal）
**未採用的理由**：功能強大但引入額外的維運負擔與學習成本。本專案的工作流複雜度（觸發 → 執行 → 判定 → 審查）遠低於需要專用引擎的門檻。過度工程。

### C. 混合：熱狀態在 Backstage、冷資料在 GitHub
**未採用的理由**：看似兩全，實則兼具兩者缺點——仍需雙寫，且增加了「什麼算熱、什麼算冷」的判斷負擔與邊界錯誤。
