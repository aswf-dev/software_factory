# ADR-003：一個工作項 = 一疊 stacked PR

- **狀態**：已接受
- **日期**：2026-08-16
- **決定者**：平台架構
- **對應**：`02-architecture.md` D3、`07-stacked-pr-workflow.md`

## 脈絡

`00-source-summary.md` §7 記載了一項具體警示：

> 只優化編碼效率的風險是——**開發期省下的時間，被更大的 code review 待辦積壓抵銷**。這是「轉移」效力而非「節省」效力。

`01-value-stream-map.md` §2.3 的分析也判定：**等待審查者有空，通常是整條價值流最長的閒置段**。

核心問題：若 agent 產能提升 5 倍而審查方式不變，結果不是快 5 倍，而是**審查佇列積壓 5 倍**——瓶頸只是從 Create 移到 Verify。

## 決策

**agent 的產出組織為一疊有序的小 PR**，而非單一大 PR。標準序列由底而頂為：

```
trunk (main)
  └── 01-test    測試/契約先行
        └── 02-impl    實作
              └── 03-docs    文件
```

工具採用 `gh stack`（已實測安裝 v0.0.2）。

## 後果

### 正面
- 審查單元縮小至 5–15 分鐘可判讀，使**認真審查成為可行**。
- 底層可先合併，問題只卡該層以上。
- 衝突局部化。
- **測試在最底層**，使審查者先看到「正確」的定義；且防堵「agent 為讓測試通過而弱化測試」——測試若已獨立審查合併，就不能事後偷改。

### 負面
- 需要 stacked PR 工具鏈，增加一項依賴（gh-stack v0.0.2 為早期版本，Q07-3）。
- agent 需要能正確拆分變更——這本身是一項不簡單的能力。
- rebase 衝突處理較單一 PR 複雜。

### 中性
- 需要明確的拆分規則與停手規則（`07` §2、§4）。
- 並非所有工作項都適合拆疊——`07` §2.3 定義了例外。

## 關鍵洞見

> **審查品質與 PR 大小非線性負相關。**

超過某個規模，審查者不再逐行讀，而是憑印象核准。那時的審查**比沒有審查更危險**——因為它製造了「已經檢查過」的錯覺。

拆分的目的是**降低審查成本**，不是為了拆而拆。若拆分後總審查成本高於單一 PR，就不該拆（`07` §2.3）。

## 替代方案

### A. 單一大 PR
**未採用的理由**：直接落入 `00` §7 警示的失敗模式。審查疲勞導致橡皮圖章，工廠的主要安全網失效。

### B. 一個工作項一顆 PR，但限制工作項大小
**未採用的理由**：把拆分責任推給 Plan 階段。但有些工作項本質上無法再拆小（一個功能就是需要測試+實作+文件），而其內部**仍可依關注點分層**。stacking 正好處理這個層次。

### C. 不拆分，改為增加審查人力
**未採用的理由**：審查容量是人類的、有限的、不可自動擴張的（`07` §6.3）。用增加人力來吸收自動化產能，等於把節省的工程時間換成審查時間——這正是「轉移而非節省」的定義。
