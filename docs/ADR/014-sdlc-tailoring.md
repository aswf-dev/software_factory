# ADR-014：SDLC 生命週期模型與裁適宣告

- **狀態**：已接受
- **日期**：2026-09-01
- **決定者**：平台工程師（Q19-4 經使用者裁決 2026-09-01：三項裁掉全數通過，各附重新檢視觸發條件）
- **對應**：`00-source-summary.md` §2（六階段）、§3（Phase 2）、SWEBOK v4 Ch10 §2.8；草案來源 `docs/19` §7（該檔由工作項 #202 併入 trunk）

## 脈絡

工廠的六階段價值流（Plan→Create→Verify→Release→Configure→Operate，`00` §2）一直是**隱式**模型：從未有任何文件宣告工廠遵循什麼生命週期模型、裁掉哪些標準流程、為什麼。

SWEBOK v4 Ch10 §2.8（Software Life Cycle Adaptation）要求：每個系統都要裁適其生命週期，並**記錄裁適理由**。沒有記錄，流程缺漏無法被檢視——「刻意裁掉」與「疏忽漏掉」在外部看來完全相同。

## 決策

### 1. 生命週期模型

採用**連續交付／lean 六階段**生命週期（`00` §2）。各階段在工廠的現行落點與主責：

| 階段 | 主責 | 工廠現行落點 |
|---|---|---|
| Plan | 人類（agent 輔助草稿） | 人類開 Issue 並附可驗證 DoD；`factory-issue-check` 預檢格式與複雜度 |
| Create | 委託 agent | 測試先行、stacked PR 逐層產出（`07` §2；`00` §3 Phase 2 Step 1） |
| Verify | agent 自動化＋人類審查 | 測試金字塔＋Quint 正式驗證（`11`、ADR-008）；每層獨立綠燈；PR 人類審查 |
| Release | 人類 | agent 產出止於合併 factory trunk；`main` 同步與版序一律由人類執行（ADR-013／Q-P2-1：agent 絕不觸碰 `main`） |
| Configure | 人類 | repo 設定（ruleset、branch protection、CODEOWNERS）由人類以 `12` 指引套用；agent 不得改 `.github/**`（停手規則 3） |
| Operate | 人類主責，agent 輔助分析 | 觀察期制度與缺陷標籤（`14`）、試跑日誌（`15`） |

### 2. 流程裁適表

處置類別：**保留**（照慣例執行，採人責或自動化）／**委託 agent**／**人類保留**（決策權明確留在人類）／**裁掉**（宣告意識性不做）。

| SWEBOK／ISO/IEC/IEEE 12207 流程 | 處置 | 理由 |
|---|---|---|
| 需求規格（acceptance criteria） | 保留（agent 輔助草稿） | DoD 必須可驗證（Ch1 §4.3）；agent 僅輔助草稿，定義權在人類（`factory-issue-check` 把关） |
| 需求追蹤（雙向） | 部分保留 | 只做「驗收條件→測試→實作」一層追蹤（Issue→PR→`Closes #N`）；含設計元素層的完整雙向追蹤對單人、工作項粒度情境過重，裁掉 |
| 需求變更控制 | 人類保留 | 以停手交還取代正式變更委員會：停手規則 4（驗收條件不明確）與「不確定就停手」；需求與 Issue 不符時的專條由 #192 補強 |
| 設計記錄 | 保留 | PR 描述「為什麼這樣做」必填（`07` §5）；架構級決策以 ADR 記錄；工作項級設計文件不強制 |
| 建構（coding） | 委託 agent | 02-impl 層由 agent 依測試先行順序實作（`00` §3 Phase 2 Step 1） |
| 測試 | 保留＋自動化 | 金字塔＋Quint 正式驗證（`11`、ADR-008）；斷言不得刪除或弱化（停手規則 6） |
| 組態管理（SCM） | 保留＋自動化 | GitHub 為唯一事實來源（ADR-001）；審查閘門以 CI＋ruleset 自動把關 |
| 釋出管理 | 人類保留 | 見上表 Release 列；工具 repo 探輕量版（人工合併 trunk、人類決定版序） |
| 維運／事故管理 | 人類保留（agent 輔助分析） | 對應 D5 自主性上限（ADR-005）：事故判斷不委託 agent |
| 根因分析（RCA） | 保留 | 缺陷標籤與期檢節奏（`14`、`15`） |
| 退休／處置（Disposal） | **裁掉** | 內部工具 repo 無外部服務義務，退休即存檔 repo，無正式處置流程可執行 |
| 正式 CCB（變更控制委員會） | **裁掉** | 單人 repo 無第二雙眼睛（Q12-4），以「停手交還人類」機制取代 |
| 容量規劃／災難復原（DR） | **裁掉（延後）** | GitHub-hosted runner 的容量與可用性由平台負責；相關殘餘風險已依 Q05-1 精神揭露，不假裝已處理 |

### 3. 「裁掉」項目的重新檢視觸發條件（Q19-4 裁決）

三項裁適各附一行觸發條件；觸發即開新 Issue 重啟檢視並修訂本 ADR。在此之前，這三個流程是**意識性不做**，不是遺漏。

| 裁掉項 | 重新檢視觸發條件（一行） |
|---|---|
| 退休／處置（Disposal） | 當本 repo 產出轉為對客戶的交付／託管件（具交付、移轉或退役義務）時。 |
| 正式 CCB | 當第二位協作者加入 repo 時（與 Q12-4 同一紀律：第二人進來即恢復正式核准機制）。 |
| 容量／DR | 當工廠改用 self-hosted runner 時（容量、可用性與復原自此成為本 repo 的責任）。 |

## 後果

### 正面
- 流程缺漏自此可被檢視：每項裁適有記錄、有理由，「裁掉」與「漏掉」可區分。
- 裁掉項附帶重啟條件，裁適不會無聲過期。

### 負面
- 宣告之後，未裁適處的缺漏即為**已知缺口**，不能再以「不知道」自解（例如：無正式 CCB、無容量規劃）。
- 六階段落點表把現行做法固定成文件；機制演進（如釋出自動化）時必須同步修訂本 ADR，否則文件與實作分岔。

### 中性
- 本 ADR 不改變任何機制，僅作宣告；機制級改善仍走各自的工作項。
- 隨附修正 `docs/ADR/README.md` 索引缺 011–013 的問題（文件衛生，非本決策的一部分）。

## 替代方案

- **直接採用 ISO/IEC/IEEE 12207 全流程**：對單人、內部工具情境過重，會產生大量空洞合規文件，違反 `00` §2「消除不必要的非加值時間」原則。未採用。
- **不宣告、維持隱式**：零成本，但流程缺漏無法被討論，直接違反 Ch10 §2.8 的裁適記錄要求。未採用。
- **採用 DevOps 三階段（Dev→Test→Ops）粗粒度模型**：丟失 Plan 與 Configure 兩個階段——而那正是工廠把人類保留決策最集中的地方（需求定義與設定權限）。未採用。
