# 06 — 人工監督政策

> **依據**：`00-source-summary.md` §6（監督三軸與 in/on the loop 定義）、§7（三大警示）、`02-architecture.md` D5（自主性上限）、`03-idp-backstage.md` §2.2（三軸 annotation）
> **讀者**：所有角色。這是工廠中**唯一決定「誰有最終決定權」的文件**。
>
> **本文件的性質**：來源研究提供的是**判斷方向**（滑動尺度），不是可執行規則。把它轉譯為**機械可判定的計分**是本專案的設計工作，不是原文內容。以下計分表的具體分數與門檻由本專案定義，需經實務校準。

---

## 1. 為什麼需要「可判定」的規則

`00` §6 的 Figure 11 給出三軸滑動尺度：業務關鍵性、風險輪廓、架構複雜度；低者 human-on-the-loop，高者 human-in-the-loop。

**但滑動尺度無法被 CI 執行。** 若把判斷留給人臨場決定，會出現三個問題：

1. **不一致**——同類工作項在不同人手上得到不同待遇。
2. **可被說服**——趕工壓力下標準會鬆動，而鬆動往往發生在最不該鬆的時候。
3. **agent 可自我裁定**——最危險的情況：agent 判斷「這個任務風險不高」然後自行合併。

因此本文件把三軸轉為 **0–2 分的客觀判準**，總分決定監督層級。**判定發生在 agent 啟動之前，由 CI 執行，agent 無權參與**。

---

## 2. 兩種監督模式的定義（`00` §6 原文）

| 模式 | 定義 | 白話 |
|---|---|---|
| **Human IN the loop** | agent 執行決策**前**需要明確、持續的人工核准 | 人先點頭，agent 才動 |
| **Human ON the loop** | agent 自主執行，人類監督，僅在例外、異常或告警時介入 | agent 先做，人看著 |

## 3. 三軸計分表

### 3.1 軸一：業務關鍵性（Business Criticality）

對應 `00` §6 的 Tactical ↔ Strategic 軸。

| 分數 | 等級 | 客觀判準（符合任一即該分） |
|---|---|---|
| **0** | Tactical | 內部工具、開發輔助、實驗性專案；故障不影響外部使用者 |
| **1** | Operational | 內部業務系統；故障影響同仁作業但不直接影響客戶 |
| **2** | Strategic | 面向客戶；或構成核心競爭優勢與智慧財產；或故障即造成營收/信譽損失 |

**資料來源**：`catalog-info.yaml` 的 `factory.io/business-criticality`（`03` §2.2）。

### 3.2 軸二：風險輪廓（Risk Profile）

對應 `00` §6 的 Low ↔ High 軸。**本軸有「碰到即滿分」的硬性規則。**

| 分數 | 等級 | 客觀判準 |
|---|---|---|
| **0** | Low | 純文件、註解、格式化、測試新增；不改動執行邏輯 |
| **1** | Medium | 一般功能程式碼；有測試覆蓋；不涉及下列硬性項目 |
| **2** | High | **觸及以下任一即為 2 分（硬性規則，無裁量空間）** |

**風險硬性規則（Hard Rules）**——變更觸及以下任一即 **risk = 2**：

| # | 類別 | 依據 |
|---|---|---|
| H1 | **授權/認證邏輯**（authn/authz、權限判斷、session 管理） | `00` §6 明列 |
| H2 | **財務計算**（金額、計費、對帳、稅務） | `00` §6 明列 |
| H3 | **敏感資料處理**（PII、憑證、加密、個資） | `00` §6 明列 |
| H4 | **systems of record 或共用模組**的介面變更 | `00` §6 明列 |
| H5 | **guardrail 自身**（`.github/`、CODEOWNERS、`catalog-info.yaml`、`.dsh/skills/`） | `05` §1.1 不變量 |
| H6 | **資料庫 schema 遷移**（不可逆或破壞性） | 本專案補充：不可逆操作 |
| H7 | **對外 API 的破壞性變更** | 本專案補充：影響下游 |

> **H5–H7 是本專案的補充**，非原文內容。H5 來自 `05` 的核心不變量；H6/H7 的理由是**不可逆性**——可回滾的錯誤與不可回滾的錯誤，風險性質根本不同。

**判定方式**：以**變更檔案路徑**與 CODEOWNERS 模式比對，機械可判定。路徑模式清單維護於 repo 的設定檔中（見 §5.2）。

### 3.3 軸三：架構複雜度（Complexity）

對應 `00` §6 的 Low ↔ High 軸。

| 分數 | 等級 | 客觀判準 |
|---|---|---|
| **0** | Low | 單一檔案或單一模組內；不新增抽象；不改介面 |
| **1** | Medium | 跨數個模組；或新增元件但沿用既有模式 |
| **2** | High | 跨服務/跨系統；或引入新的架構模式；或改動共用抽象 |

**資料來源**：`catalog-info.yaml` 的基礎值，並可由變更範圍（觸及的模組數）動態調升。

> ⚠️ **本軸最難自動判定**。第一階段建議：以 `catalog-info.yaml` 的靜態值為主，輔以「觸及目錄數 ≥ 3 則至少 1 分」的粗略規則。這是已知的近似（Q06-2）。

## 4. 總分與監督層級

三軸相加，總分 0–6：

| 總分 | 監督層級 | agent 權限 | 人類角色 |
|---|---|---|---|
| **0–1** | **Human ON the loop** | 可建立 PR **並自動合併**（須另符合 §4.1 全部條件） | 事後抽查；異常時介入 |
| **2–4** | **人類審查必要** | 可建立 PR，**不得合併** | 逐一審查並核准 |
| **5–6** | **Human IN the loop** | **僅可產出分析與方案，不得實作** | 主導設計與實作 |

> **本專案對原文的一項補充**：`00` §6 只區分 human-in-the-loop 與 human-on-the-loop **兩級**。本專案在中間增設「人類審查必要」（2–4 分）這**第三級**，對應標籤 `oversight/review`。
>
> 增設理由：兩分法會迫使大量中等風險工作被歸入 in-the-loop（agent 完全不參與），浪費 agent 在「可產出但需審查」情境的價值。第三級讓 agent 承擔產出、人類專注判斷，是本專案認為更符合實務的切分。**這是設計判斷，非原文內容。**

### 4.1 自動合併的附加條件（全部滿足才可）

總分 0–1 是**必要非充分**條件。自動合併還須同時滿足：

- [ ] 屬於 `00` §6 明列的 on-the-loop 類別（見 §4.2）
- [ ] `catalog-info.yaml` 的 `factory.io/agent-automerge` 不為 `"false"`
- [ ] 所有 required checks 通過
- [ ] 未觸及任何 CODEOWNERS 保護路徑
- [ ] 變更行數 **≤ 200 行**（⚠️ 待校準，Q06-3）

> **注意：此處的 200 行與 `07` §2.2 的「200–300 行」是兩個不同語意的數值，不可混用**：
> - **本處（≤ 200 行）**＝ **自動合併的准入門檻**——超過即失去自動合併資格，退回人類審查。
> - **`07` §2.2（200–300 行）**＝ **拆分的建議上限**——超過則建議再拆，屬撰寫指引而非閘門。
>
> 兩者刻意不同：自動合併的門檻應**嚴於**一般拆分建議。因此一顆 250 行的 PR 是合規的拆分，但**不符合自動合併資格**。
- [ ] 未觸發任何 `factory-stop-rules` 條款

> **類型級限制（工作類型唯一施力點）**：因 `task_type` 不進入計分（§5.2 註記），自動合併閘門對「工作類型」完全無感——計分程式（`src/scoring/score.ts`）機械判定的只有：總分 0–1、擁有者否決、硬性規則觸發、變更行數上限（200）。清單第一條（屬於 §4.2 明列類別）因而是**類型語意唯一的施力點**：宣告為語意高風險的任務（如安全修復類工作），只能靠這條擋下，而該條由審查者於 PR 審查時判斷、非計分程式判定。相關局限見 §8 局限 3。
>
> **機械化的類型級限制（2026-10-05 補記）**：計分之後另有一層**不改計分**的類型規則（`src/pipeline/no-automerge.ts` 的 `NO_AUTOMERGE_TASK_TYPES`）：`agent-write-spec`（ADR-018 護欄②）與 `agent-pbt-audit`（ADR-019 §5，試行期）即使計分允許，也一律降為 ready-for-review。反方向的 in-loop 放行同樣按類型：`OUTPUT_ONLY_TASK_TYPES`（analyze、propose-skill）與 `IN_LOOP_ALLOWED_TASK_TYPES`（pbt-audit，前提是 crosscheck 只放行 PBT 測試檔，且在 `NO_AUTOMERGE_TASK_TYPES` 內）。兩者都只收緊或在白名單前提下放行，tier 與標籤不變。

> **設計理由**：任一條件不滿足即退回「人類審查必要」。這是**單向棘輪**——條件只能收緊不能放寬，且 `factory.io/agent-automerge: "false"` 給予服務擁有者無條件否決權（`03` §2.2）。

### 4.2 明確允許自動合併的類別（`00` §6 原文清單）

原文明列的 human-on-the-loop 範例，本專案照收：

- 內部業務賦能應用
- 小型 bug 修復、相依套件更新、設定變更
- 全庫重構以修正程式碼異味或替換已棄用的函式/API
- 產生程式碼與架構文件
- 產生單元測試套件、測試案例或測試資料
- 自主工作負載最佳化

### 4.3 明確要求 human-in-the-loop 的類別（`00` §6 原文清單）

- 策略性活動：產品管理、功能優先排序、理解複雜使用者需求、軟體架構
- 建構構成核心智慧財產的業務關鍵軟體
- 處理財務計算、敏感資料或授權邏輯相關程式碼
- 設計影響 systems of record 或共用模組的新功能與架構變更
- 驗證業務關鍵或安全關鍵用途的 AI 生成解法

> **注意 §4.3 最後一條**：「驗證 AI 生成的解法」本身就是 human-in-the-loop 工作。**agent 不得驗證自己的產出並據以放行**——這是 `05` §6 提到的複合風險（agent 互相確認彼此的錯誤）在單 agent 情境的版本。

## 5. 判定的執行方式

### 5.1 判定時機與執行者

```
Issue 建立/標記 ready
      │
      ▼
[CI 計分]  ← 由 GitHub Actions 執行，agent 無權參與
      │
      ├─ 5–6 分 ─► 貼 oversight/in-loop → 不啟動 agent → 通知人類
      ├─ 2–4 分 ─► 貼 oversight/review  → 啟動 agent（禁止合併）
      └─ 0–1 分 ─► 貼 oversight/on-loop → 啟動 agent（可自動合併）
```

**關鍵性質**：判定在 **agent 啟動之前**完成。agent 收到的是**已決定的權限**，而非可協商的建議。

### 5.2 計分的資料來源

| 輸入 | 來源 | 可否被 agent 修改 |
|---|---|---|
| 三軸基礎值 | `catalog-info.yaml` | ❌ 受 CODEOWNERS 保護（`05` §2.2） |
| 風險硬性規則路徑 | `.github/factory/risk-paths.yml` | ❌ 在 `.github/` 下，受保護 |
| 變更範圍 | 執行後的 diff | ⚠️ 見 §5.3 |
| 自動合併否決 | `factory.io/agent-automerge` | ❌ 受保護 |
| 工作類型（`task_type`） | Issue 本文——**不是計分輸入**（見下方註記） | —（計分程式不讀取） |

> **註記（計分與任務類型正交）：工作類型（`task_type`）不是計分輸入。**
> 計分程式的輸入（實作見 `src/scoring/types.ts` 的 `ScoreInput`）只有上表的標註（annotations）、變更路徑、變更行數與硬性規則路徑模式四項——任務類型（如 `agent-write-docs`、`agent-fix-bug`）**完全不進入計分**，不會抬高或降低任何一軸分數。這是刻意設計而非缺陷：Issue 本文可能由 agent 起草（`factory-draft`），若類型進入計分，等同讓被判定者參與判定，直接抵觸 §5.1「agent 無權參與判定」。
> `task_type` 的實際用途：格式檢查（`factory-issue-check` 要求該欄位存在，write-spec／pbt-audit 另有專屬欄位或範圍檢查）、模型路由與複雜度**建議**（`factory-model`；該建議以留言展示、不進入監督計分，見 §8 局限 2）、派工辨識（task-template、crosscheck 白名單模式、類型專屬 skill 派送），以及 §4.1 補記的類型級限制。類型語意若承載高風險，唯一的施力點是 §4.1 的「類型級限制」；計分後果見 §8 局限 3。

```yaml
# .github/factory/risk-paths.yml — 風險硬性規則的路徑模式
# 觸及任一模式即 risk = 2
hard_rules:
  H1_auth:      ["src/auth/**", "**/authorization*", "**/*permission*"]
  H2_financial: ["src/payment/**", "src/billing/**", "**/*invoice*"]
  H3_sensitive: ["**/*pii*", "**/crypto/**", "**/*secret*"]
  H4_shared:    ["src/shared/**", "src/core/**"]
  H5_guardrail: [".github/**", "CODEOWNERS", "catalog-info.yaml", ".dsh/skills/**"]
  H6_migration: ["migrations/**", "**/*schema*"]
  H7_api:       ["api/**", "**/*.proto", "openapi.yaml"]
```

> ⚠️ 路徑模式須依實際 repo 結構調整；上例為示意。

### 5.3 二次判定（重要的補漏）

**問題**：初次計分發生在 agent 執行**之前**，此時尚不知道會改動哪些檔案。若 agent 的變更意外觸及高風險路徑（如為修 bug 而改到授權邏輯），初次判定就過期了。

**解法**：PR 建立後**重新計分**：

```
agent 產出 PR → [二次計分：以實際 diff 為準]
                      │
                      ├─ 分數上升 ─► 升級監督層級，撤銷自動合併資格
                      └─ 分數未變 ─► 依原判定續行
```

> **單向規則**：二次判定**只能升級、不能降級**。agent 的實際行為只會讓監督變嚴，不會變鬆。這防止「先用低風險描述取得寬鬆權限，再做高風險改動」的路徑。
>
> 此規則同時由 GitHub 層機制執行：即使二次計分邏輯失效，CODEOWNERS 仍會對高風險路徑強制人類審查（D4 雙層防護）。

## 6. 計分範例

| 情境 | 關鍵性 | 風險 | 複雜度 | 總分 | 判定 |
|---|---|---|---|---|---|
| 內部工具補單元測試 | 0 | 0 | 0 | **0** | on-loop，可自動合併 |
| 內部工具更新相依套件 | 0 | 1 | 0 | **1** | on-loop，可自動合併 |
| 客戶端服務修 UI 文案 | 2 | 0 | 0 | **2** | 人類審查 |
| 內部系統修一般 bug | 1 | 1 | 1 | **3** | 人類審查 |
| **任何服務改到授權邏輯** | — | **2** | — | **≥2** | 人類審查；若關鍵性 2 + 複雜度 1 則 **5 → in-loop** |
| 客戶端服務改金流計算 | 2 | 2 | 1 | **5** | **in-loop，agent 不得實作** |
| 跨服務架構重構 | 2 | 2 | 2 | **6** | **in-loop，agent 不得實作** |
| 修改 CI 設定 | — | **2**(H5) | — | ≥2 | 人類審查；且 agent **無權限**執行（D6） |

> **最後一列的雙重保護值得注意**：即使計分只判定為「人類審查」，D6 的 App 權限設計已使 agent **根本無法**修改 workflow。計分是政策層，權限是機制層——**機制層不依賴政策層正確**。

## 7. 政策的例外處理

### 7.1 緊急情況（如生產事故）

**規則**：緊急情況**不放寬** agent 的權限，而是**移除 agent**。

事故處理由人類直接進行。理由：`00` §7 的技能退化警示——最需要人類判斷的時刻，恰是最不該依賴 agent 的時刻。若團隊只在平時能處理事故（因為平時有 agent），那是能力的假象。

### 7.2 政策放寬的程序

任何放寬（如調降某類別的分數、放寬自動合併行數上限）必須：

1. 修改本文件並說明理由；
2. 經 platform-team 審查（本文件受 CODEOWNERS 保護）；
3. 附上支持該放寬的**實際數據**（如：該類別連續 50 次自動合併零缺陷）。

> **不接受的放寬理由**：「太慢了」「agent 表現一直很好」「這次很趕」。前兩者需要數據支持，第三者是恰恰要拒絕的情況。

## 8. 本政策的局限（誠實揭露）

1. **分數與門檻未經實務校準**——0–1 為自動合併、5–6 為 in-loop 的分界是**設計判斷**，非實證結論。第 1 期結束後應以實際缺陷率檢視。
2. **複雜度軸的自動判定最弱**（§3.3），目前依賴靜態標註。⚠️ **2026-08-25（ADR-011）部分落地**：`src/issue-analysis/complexity.ts` 已把 §3.3 的判準機械化（scope 關鍵字、檔案/模組數、風險關鍵字），供 `factory-issue-check` 留言建議與 `factory-run` 模型路由使用；但該分析**不進入監督計分**（監督仍以 catalog 標註＋路徑為準），誤判以「留言展示判據＋人工覆寫」緩解。
3. **路徑比對無法涵蓋語意風險**——檔案不在高風險路徑下，不代表改動無風險。CODEOWNERS 與人類審查是此局限的補償。**根因**：工作類型不是計分輸入（§5.2 註記），計分對類型語意「全盲」——任務無論自稱何種類型（即使是安全修復性質的工作），只要路徑未觸及硬性規則，三軸分數不會因此上調；類型級限制僅存於 §4.1 的審查清單，屬人工判斷而非機械計分。
4. **`catalog-info.yaml` 的三軸值依賴人類誠實登錄**。若登錄不實，整個政策失效。建議定期抽查。
