# 31 — 方法論入口（給第一次開單的人）

> **讀者**：**沒有軟體工程背景**、或第一次使用這套工廠的人。不需要先讀懂任何其他文件。
> **這份文件要解決什麼**：工廠不缺流程（`docs/19` 已對照 SWEBOK v4 補完並實作），缺的是**在你要動手的當下，有人告訴你「這張單還缺什麼、該先做什麼」**。
> **讀完你應該能做到**：判斷該開哪一種工作單、知道它必須先有什麼、知道去哪裡找一個可以照著改的範例。

---

## 0. 一句話理解這套工廠

你**用 GitHub Issue 描述要做的事**，工廠派一個 AI agent（DSH）去目標 repo 做事，**產出一疊小 PR** 給你審查。

有兩件事**永遠是人做的**，工廠不會替你做，這不是缺陷而是刻意設計：

1. **決定要做什麼**（規劃）。
2. **審查並核准**（`docs/06`）。

工廠能自動化的是「**理解現況、建立安全網、驗證**」三類工作；「**決策**」與「**結構性搬移**」不能（`docs/29` §3.4）。所以你要是不知道該做什麼，**工廠幫不了你**——它能幫你把「已經想清楚的事」又快又安全地做完。

---

## 1. 先問自己四件事

照順序回答，就會得到「該開哪張單」：

### Q1：我只是想搞清楚狀況，還是要改東西？

- **只想搞清楚** → 開 `agent-analyze`。**不產生程式碼變更**，只產報告。這是最安全的第一步，也是唯一在最高風險（`in-loop`）級別還能跑的類型之一。
- **要改東西** → 繼續 Q2。

### Q2：這是「既有行為」還是「新功能」？

- **既有行為**（有東西壞了、或既有程式碼缺測試）→ 繼續 Q3。
- **新功能、重構、大規模搬移** → **停。**
  > **現有 7 種工作類型中，沒有任何一種能實作新功能或重構**（`docs/29` §3.4 明載此為已知缺口）。這類工作目前**由人類執行**；工廠只能幫你分析、寫文件、補測試、跑驗證。
  > 另外，需求**還沒說清楚**時，可以先開 `agent-write-spec` 產出規格草稿——但它有硬性前置，見 `docs/28` §1。

### Q3：那個模組現在有測試嗎？

- **有可跑的測試** → 開 `agent-fix-bug`（測試先行：先寫一個會紅的測試，再修到綠）。
- **沒有測試** → **先開 `agent-add-tests`**，等它合併後再開 `agent-fix-bug`。
  > 為什麼要分兩張單？因為 `agent-fix-bug` 的整個安全性依賴「先有一個會紅的測試」（`docs/07` §2.1）。沒有測試就修 bug，等於**沒有任何東西能證明你真的修好了**。

### Q4：這是不是在改「工廠自己的規則」？

**是** → 停手。改 CI 設定、branch protection、`CODEOWNERS`、`catalog-info.yaml`、`.dsh/skills/**` 一律**由人類執行**（`factory-stop-rules` 第 3 條；`risk-paths.yml` H5）。agent 碰到會直接停手並交還給你。

## 2. 對照表（最快的答案）

| 你想做的事 | 開哪一張 | 必須先有什麼 | 範例 |
|---|---|---|---|
| 搞清楚某處為什麼壞、影響範圍多大 | `agent-analyze` | 無 | `docs/33` §1 |
| 替既有行為補測試 | `agent-add-tests` | 目標 repo 的測試能跑 | `docs/33` §2 |
| 修一個有明確重現步驟的缺陷 | `agent-fix-bug` | **該模組已有測試**（否則先 `agent-add-tests`） | `docs/33` §3 |
| 需求還說不清楚，先產規格 | `agent-write-spec` | **人類撰寫或逐條確認**的規格來源（`docs/29` §10.2） | `docs/28` |
| 該模組缺性質測試，想事後稽核 | `agent-pbt-audit` | Hegel 依賴精確釘版、`.gitignore` 含 `.hegel/`（`docs/30`） | `docs/33` §5 |
| 更新相依套件 | `agent-update-deps` | 無特別前置 | `docs/33` §4 |
| 補文件（不是拿來當規格） | `agent-write-docs` | 無 |
| 想把重複出現的經驗寫成新技能 | `agent-propose-skill` | 同一類缺口出現 ≥3 次（`docs/25` §3） |
| 新功能、重構、拆單體 | **人類執行** | — | `docs/29` §11 |

**「允許類型」與就緒度的關係**：棕地導入時有規模（S/M/L）與就緒度（R0–R2）分級，不同等級允許的類型不同（`docs/29` §5）。**該對照目前沒有機械強制**（`docs/29` §5 自承），由開單者自律、審查者把關。不確定時**先開 `agent-analyze`**——它幾乎在任何情況下都安全。

## 3. 送出之後會發生什麼

```
你開 Issue
   │
   ▼
factory-issue-check 檢查格式 ＋ 回一張「提示卡」（零成本，不合規會擋下）
   │   ├─ ✅ 格式合規
   │   ├─ 📊 複雜度分析 ＋ 🤖 建議模型
   │   ├─ 💡 DoD 具體性提示        ← 你的驗收條件夠不夠具體
   │   ├─ ⚠️ 事前風險路徑提示      ← 你的單會不會強制人類審查
   │   ├─ 🔖 需求追蹤編號 REQ-1…   ← 給 agent 報告用
   │   └─ 🧭 規劃健檢              ← **你的單還缺什麼、該先做什麼**
   ▼
三軸計分（業務關鍵性 × 風險輪廓 × 複雜度，0–6 分，`docs/06` §3）
   ├─ 0–1 on-loop：agent 執行，可自動合併
   ├─ 2–4 review ：agent 執行，需人類審查
   └─ 5–6 in-loop ：**不啟動 agent**，人類主導
   ▼
agent 執行 → 產出 stacked PR → 人類審查 → 合併
```

**你要看懂的是那個提示卡**：它是工廠唯一在「你還沒花錢」時跟你講話的地方。**不合規會 `exit 1` 停止派工**——先修正再重送。

### 三軸分數怎麼來的（`docs/06` §3）

| 軸 | 0 | 1 | 2 |
|---|---|---|---|
| 業務關鍵性 | 內部工具／實驗 | 內部業務系統 | 面向客戶／核心競爭力 |
| 風險輪廓 | 純文件、純測試 | 一般功能程式碼 | **觸及 H1–H7 硬規則即 2 分**（無裁量空間） |
| 複雜度 | 單檔、單一關注點 | 多檔 | 跨模組、架構級 |

分數**不是**由 agent 決定的，也不是由你自由心證：業務關鍵性讀 `catalog-info.yaml` 的標註，風險輪廓由 `risk-paths.yml` 的 glob 客觀比對（`docs/06` §3.2）。**未標註的軸一律 fail-safe 判 2 分**——這就是為什麼「什麼都沒標」的 repo 會直接落到人類主導。

## 4. 「我想不到該怎麼寫」的四段式

PRD 只要四段（`src/factory-draft/prompts.ts` 也是照這四段檢查的）。**缺一段就寫不出可驗證的驗收條件**：

```
目標模組 / 檔案：src/scoring/resolve-axis.ts
做什麼（一句話）：修正 changedLines 為 0 時被誤判為 low 的問題
為什麼：上線後發現純文件 PR 被自動合併（應為 medium）
範圍（不碰什麼）：不動評分門檻值，不動 catalog-info.yaml
```

驗收標準（DoD）三項是**形式契約，固定勾選**；真正的工作是補上**這張單專屬、可被第三方驗證**的條目：

- ❌ 不好：「確認計分正確」（沒有可觀察結果，是空泛詞彙）
- ✅ 好：「`changedLines=0` 的輸入回傳 `low`；`npm run test:unit` 新增 3 則案例全綠」

詳見 `docs/32` §2、§3。

---

## 5. 誠實的邊界（你應該知道工廠做不到什麼）

| 工廠做不到 | 為什麼 | 你該怎麼做 |
|---|---|---|
| 替你想「該做什麼」 | 規劃是人類專屬（`ADR-005`、`docs/24` §3） | 先開 `agent-analyze` |
| 實作新功能或重構 | 現有類型無法勝任（`docs/29` §3.4） | 人類執行 |
| 保證你的驗收條件是對的 | 它只檢查「可觀察、不含空泛詞彙」的形式 | 自己確認，或找懂的人覆核 |
| 檢查你的前置工作項是否已完成 | 規劃健檢不做 GitHub 查詢（`docs/32` §4） | **自己確認前置已合併** |
| 代替人類審查 | 審查容量是人的、有限的、不可自動擴張（`docs/07` §6.3） | 沒讀懂就不要核准 |
| 在單人 repo 給你第二雙眼睛 | GitHub 禁止自我核准，本 repo 目前只有一位協作者（`docs/12` §2.1，已知缺口） | 這條紀律只能靠自律 |
