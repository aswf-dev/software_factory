# 33 — 工作項範例（可直接複製）

> **讀者**：還不確定自己的 Issue 該怎麼寫的人。**用法**：找到最接近你情況的範例，整段複製，改內容。
> **前提**：先讀 [`docs/31`](31-methodology-entry.md) 決定類型，再讀 [`docs/32`](32-writing-work-items.md) 了解每個欄位為什麼這樣寫。

**素材來源與誠實標註**：以下範例取自本 repo **真實執行過**的工作項（`docs/15` 試點 #2／#3、`docs/20` 的 B1／B2／C1）。PRD 與驗收條件**依實際內容改寫為可複製的教學形式**，並逐一標明數據出處；**未經實跑驗證的類型**（`agent-write-docs`／`agent-update-deps`／`agent-write-spec`／`agent-propose-skill`）另立 §6，**只示範 Issue 寫法，不假造執行結果**。

---

## 1. `agent-analyze` — 先搞清楚狀況（最安全的第一步）

**什麼時候用**：不確定根因、不確定影響範圍、不確定該不該做。**不產生任何程式碼變更。**
**實跑狀態**：✅ 已驗證（Issue #227 ＋ 試點 T1／T2／T3，`docs/29` §3.1）

```
### 任務類型

agent-analyze

### 需求描述（PRD）

目標模組 / 檔案：src/usage/session-log.ts

做什麼（一句話）：調查 session log 回放偶爾漏算 token 的原因與影響範圍

為什麼：factory-usage 的報告數字是成本決策依據；漏算會讓 SR7 的 token 預算判斷失準

範圍（不碰什麼）：
- 不修改任何程式碼，只產出分析報告
- 不碰 docs/08 的指標定義
- 不碰 .github/workflows/**

### 驗收標準（DoD）

- [x] 有可驗證的測試/驗證方式（測試紅→綠或明確驗證命令）
- [x] 不觸碰高風險路徑（H1–H3 等硬規則，見 risk-paths.yml）
- [x] 跑測試確認綠燈（不跑需外部服務的 E2E）

報告須含：結論摘要、證據與根因、影響範圍、方案比較（含被拒方案）、建議下一步
```

**為什麼這樣寫**：
- 產出位置與格式由類型固定（`docs/29` §3.1）：報告放 `docs/research/<issue>-<主題>.md`，必含五段。把要求寫進驗收條件，`factory-issue-check` 就能辨識成可驗證條目。
- 「範圍：不修改任何程式碼」是這類型的核心紀律——**分析單不得變成實作單**。

**預期結果**：單層 PR（只有報告）。**不會出現** `src/` 變更。
**常見寫錯**：把「順便修一下」寫進 PRD → 派工後會被 crosscheck 判超出範圍，或 agent 依第 11 條停手。

## 2. `agent-add-tests` — 替既有行為補測試

**什麼時候用**：某段既有程式碼沒有測試，或測試不足。**新測試必須在既有實作上直接綠燈。**
**實跑狀態**：✅ 已驗證（試點 #2，fubon-tradingbot Issue #569 → PR #570，+33 行，單層）

```
### 任務類型

agent-add-tests

### 需求描述（PRD）

目標模組 / 檔案：test/jest/TimeUtils.test.ts

做什麼（一句話）：為 TimeUtils 的既有函式補單元測試（含邊界案例）

為什麼：TimeUtils 是排程判斷的共用工具，目前無測試覆蓋；後續要改它時沒有安全網

範圍（不碰什麼）：
- 不修改任何 src/ 下的實作（只能新增測試檔）
- 測試必須在既有實作上直接綠燈
- 若測試揭露既有缺陷：以 it.skip 交付（保留完整斷言）＋在 Issue 留言報告，不自行修實作

### 驗收標準（DoD）

- [x] 有可驗證的測試/驗證方式（測試紅→綠或明確驗證命令）
- [x] 不觸碰高風險路徑（H1–H3 等硬規則，見 risk-paths.yml）
- [x] 跑測試確認綠燈（不跑需外部服務的 E2E）

- 新增的測試在未修改 src 的前提下全綠
- 覆蓋至少 3 個邊界案例：空輸入、跨午夜區間、單點時間
- 不刪除或弱化既有斷言
```

**為什麼這樣寫**：
- **單層**（只有 `01-test`）。`agent-add-tests` 不需要三層 stack——沒有實作層也沒有文件層。
- 先講明「揭露缺陷時怎麼辦」：這是最容易出錯的地方。正確路徑是 `it.skip` ＋ 留言建議另開 `agent-fix-bug`（`docs/19` §6.6 第 2 點），**不是**順手修掉。
- 驗收條件寫出具體案例數與案例內容 → 可被第三方逐條核對。

**預期結果**：`factory/569-01-test` 分支 → 單一 PR，base 為目標 repo 的 `software-factory` 分支。
**常見寫錯**：同時要求「補測試」與「修 bug」→ 拆成兩張單，順序是先 `agent-add-tests` 再 `agent-fix-bug`（`docs/32` §4）。

## 3. `agent-fix-bug` — 修一個有明確重現步驟的缺陷

**什麼時候用**：有明確重現步驟，且**該模組已有測試**。
**實跑狀態**：✅ 已驗證（試點 #3，fubon-tradingbot Issue #571 → 三層 stack #572/#573/#574，`docs/15` §2.4）

```
### 任務類型

agent-fix-bug

### 需求描述（PRD）

目標模組 / 檔案：src/utils/TimeUtils.ts

做什麼（一句話）：修正 isWithinTimeRange 不支援跨午夜區間（如 22:00–02:00）的問題

為什麼：同 repo 的 SessionHelpers 已正確實作跨午夜語義，兩者行為不一致；夜間排程判斷會誤判

範圍（不碰什麼）：
- 只改 isWithinTimeRange 及其測試，不改其他時間工具函式
- 不改變白天（同日）區間的既有行為
- 不碰 catalog-info.yaml

### 驗收標準（DoD）

- [x] 有可驗證的測試/驗證方式（測試紅→綠或明確驗證命令）
- [x] 不觸碰高風險路徑（H1–H3 等硬規則，見 risk-paths.yml）
- [x] 跑測試確認綠燈（不跑需外部服務的 E2E）

- 新增測試「跨午夜區間」在修改前為紅燈、修改後為綠燈
- 同日區間（09:00–17:00）的既有測試維持全綠
- 與 SessionHelpers 的跨午夜語義一致
```

**為什麼這樣寫**：
- **明確寫出「修改前紅、修改後綠」**——這是 `agent-fix-bug` 的全部安全性所在（`docs/07` §2.1）。沒有紅燈的修復無法證明真的修好了。
- 用「與 X 不一致」當「為什麼」：這是可被審查者驗證的理由，不是主觀偏好。
- 「不改同日行為」把回歸風險寫進驗收條件。

**預期結果**：三層 stack `factory/571-01-test` → `-02-impl` → `-03-docs`（只有 01-test 置底，是為了防堵弱化測試）。
**常見寫錯**：

- 只給「會壞」不給重現步驟 → agent 依第 4 條停手（驗收條件不明確）。
- 目標模組還沒有測試檔 → **先開 `agent-add-tests`**（規劃健檢會提醒你）。
- 把「順便重構一下」寫進去 → 重構要另開單，且目前**沒有對應類型**（`docs/29` §3.4）。

## 4. `agent-update-deps` — 升級相依套件

**什麼時候用**：升級版本、修補已知漏洞。**未經人類核可不得新增套件**（`factory-stop-rules` 第 5 條）。
**實跑狀態**：⚠️ **從未實跑**（`docs/29` §3.1）——以下只示範 Issue 寫法

```
### 任務類型

agent-update-deps

### 需求描述（PRD）

目標模組 / 檔案：package.json

做什麼（一句話）：將 minimatch 由 10.2.6 升級至最新修補版，以清除 audit 的高風險發現

為什麼：pnpm audit --audit-level=high 在 CI 會擋下（test.yml），目前阻擋主線

範圍（不碰什麼）：
- 只改 package.json 與 lockfile，不改任何原始碼
- 不新增任何未在 lockfile 出現過的套件
- 不動 overrides 以外的傳遞相依

### 驗收標準（DoD）

- [x] 有可驗證的測試/驗證方式（測試紅→綠或明確驗證命令）
- [x] 不觸碰高風險路徑（H1–H3 等硬規則，見 risk-paths.yml）
- [x] 跑測試確認綠燈（不跑需外部服務的 E2E）

- `pnpm audit --audit-level=high` 退出碼為 0
- `npm test` 全綠（升級未造成回歸）
- lockfile 的變更只涉及該套件及其傳遞相依
```

**注意**：這類單通常**單一 PR**、不 stack（`docs/07` §2.3）。若升級造成測試紅燈且無法在不放寬斷言的前提下修好 → agent 依第 6 條停手交還。

## 5. `agent-pbt-audit` — 事後稽核性質測試

**什麼時候用**：模組已有測試，但想用性質測試（property-based testing）找邊界缺陷。
**實跑狀態**：⚠️ 從未實跑；前置作業要求見 `docs/30`、`ADR-019`

```
### 任務類型

agent-pbt-audit

### 需求描述（PRD）

目標模組 / 檔案：src/options/TickSizeCalculator.ts

做什麼（一句話）：以 Hegel 稽核價格檔位換算模組，找出既有範例測試未覆蓋的邊界缺陷

為什麼：檔位換算是數值計算，邊界進位錯誤不易靠範例測試發現

範圍（不碰什麼）：
- 只新增 PBT 測試檔，不修改產品程式碼
- 不改既有的範例測試
- 找不到有依據的 property 就停手說明，不寫沒有依據的 property

### 驗收標準（DoD）

- [x] 有可驗證的測試/驗證方式（測試紅→綠或明確驗證命令）
- [x] 不觸碰高風險路徑（H1–H3 等硬規則，見 risk-paths.yml）
- [x] 跑測試確認綠燈（不跑需外部服務的 E2E）

- 每條 property 都有 // source: 引用（INV_* / Issue 驗收條件 / 既有行為）
- smoke property 通過後才進行完整既定案數的執行
- 不得以 skip 規避失敗，失敗須附反例
```

**前置條件（不滿足就別送）**：目標 repo 的 Hegel 依賴已精確釘版、`.gitignore` 含 `.hegel/`。否則派工時直接失敗（`docs/30`）。

**注意「目標模組 / 檔案」必須恰好一個路徑**——這是稽核範圍，由 `factory-issue-check` 機械檢查（`ADR-019` R3）。填兩個路徑會被擋。

## 6. 尚未試跑成功的類型（只示範 Issue 形狀）

`docs/29` §3.1 明載以下類型**沒有成功實跑紀錄**。依 `docs/29` §6 的**試驗場規則**：每一型都必須先在小型專案試點成功至少 1 次，才能用在中型與大型專案；**尚未試點成功的類型，在中大型專案中由人類代行該步驟**。

| 類型 | 給誰用 | Issue 撰寫要點 | 手冊 |
|---|---|---|---|
| `agent-write-docs` | 補文件（**不得當規格來源**） | PRD 明寫「只寫文件、不改程式碼」；範圍不得包含 `src/` | — |
| `agent-update-deps` | 相依升級 | 見 §4 | — |
| `agent-write-spec` | 產出可執行規格 | **必填**「規格名稱」（kebab-case）與「規格來源」（repo 內路徑或 `issue`，**不接受 URL**）；規格來源必須是人類撰寫或逐條確認的業務規則 | [`docs/28`](28-write-spec-runbook.md) |
| `agent-propose-skill` | 把重複 3 次以上的經驗寫成技能草案 | 只寫 `proposals/skills/<name>/SKILL.md`，**不會生效**——須人類執行 `factory-skills-lock --promote` | [`docs/25`](25-skill-authoring-loop.md) |

**重要**：`agent-write-docs` 依程式碼寫出的文件**不能當規格來源**——照實作寫不變量會把缺陷一起當成正確（`docs/29` §10.2）。若你的目的是餵規格流程，請改為由領域專家撰寫或逐條確認的業務規則。

## 7. 六個最容易犯的錯

| 錯誤 | 後果 | 正確做法 |
|---|---|---|
| PRD 沒寫「目標模組 / 檔案」 | 無法在花錢前比對風險路徑；留言出現提示 | 寫上真實路徑，或先開 `agent-analyze` |
| 驗收條件只勾三個固定項，沒補專屬條目 | DoD 具體性提示；無法判斷「完成」 | 補至少一條含可觀察結果的條目 |
| 寫「優化」「完善」「確認沒問題」 | 命中空泛詞彙提示 | 改寫成命令／輸出／斷言／量化閾值 |
| 一張單同時要求「補測試」與「修 bug」 | 順序衝突，安全網失效 | 拆兩張，先 `agent-add-tests` |
| 要求改 CI 設定／`CODEOWNERS`／`.dsh/skills/**`／PBT 測試檔 | `factory-issue-check` 擋下，或 agent 停手 | 由人類執行 |
| 有前置卻沒填欄位，或填了沒確認前置已合併 | 白花 token（前置未完成時多半一定停手） | 填「前置工作項」，並**自己確認已合併** |
