# 24 — 多 agent 協作的複合風險治理細則（Q05-5）

> **依據**：`05-guardrails-governance.md` §6.1（自主性階梯的分級治理）、`ADR-010`（多 agent 團隊工具延後採用）、`docs/research/230`（Warp DeepWiki 實證）
> **用途**：補齊 `docs/10` Q05-5——「引入多 agent 前必須先補」的複合風險治理細則。本文件的存在**不代表採納多 agent**；它是 ADR-010 觸發條件 1 的滿足物，也是日後真要引入時的既定規則。

## 2. 五項治理細則

以下五項對應 `docs/05` §6.1 所列的必補項目。**任一項未落實，不得引入多 agent。**

### 2.1 細則 1：spawn 需人類確認，agent 不得自主組隊

**規則**
1. 任何「由 agent 啟動另一個 agent」的動作，**必須經人類明示確認**後才執行。
2. 確認的對象是**編排計畫**：要啟動幾個、各自任務、模型、權限範圍、預期產出。
3. **禁止遞迴 spawn**：被啟動的 agent 不得再啟動下一層。深度上限為 1。
4. CI 環境無人可確認 → **等同拒絕**（沿用 `factory-guardrail.patch.yml` 的 `approval: never` 語意：需要核准的操作立即失敗，而非等待逾時）。

**依據**：證據 D；`docs/05` §6.1「人類審查在 D5 的範圍內永不移除」。

**為何禁止遞迴**：深度 2 以上時，人類確認的是「計畫的計畫」，實際執行內容已不可預見——確認淪為形式。

---

### 2.2 細則 2：審查者 agent 的產出僅為附加意見

**規則**
1. 審查者 agent 的輸出**一律標記為 advisory**，寫入 PR 留言或 report 的獨立區段。
2. **不得**成為任何 gate 的輸入：不影響 `runWorkItem` 的終態判定、不影響標籤、不影響合併權限。
3. **不得**取代人類審查；`CODEOWNERS` 的要求不因存在審查者 agent 而放寬。
4. 審查者 agent **不得審查自己所屬團隊的產出**（避免自我確認）。

**依據**：`docs/05` §6.1「審查者 agent 的產出不得取代人類審查，只能作為附加意見」；`docs/06` §4.3「agent 不得驗證自己的產出並據以放行」。

**實作約束**：若引入，`src/pipeline/run-work-item.ts` 的 `PipelineInput` **不得**新增審查者 agent 的欄位——這是機制層的保證，勝過提示層的約定。

---

### 2.3 細則 3：缺陷歸因與棘輪延伸到團隊

**規則**
1. **團隊為單一歸因單元**：任一成員產生的缺陷，歸因於**整個團隊**，不細分到個別 agent。
2. `defect/escape`／`defect/review` 的標記對象仍是**工作項 Issue**，不變。
3. **棘輪照常運作**：`ADR-005` 的不對稱設計（放寬需數據、收緊只需一次事故）適用於團隊——任一自動合併類別出現缺陷逃逸，**立即收回該類別**，不因「是別的 agent 造成的」而豁免。
4. 團隊模式的樣本**與單 agent 樣本分開統計**——兩者的缺陷率不可混算（`docs/15` §2.5 的多 repo 分開統計原則同理）。

**依據**：`ADR-010`「維持『單一帳戶單元』的缺陷歸因與棘輪機制不被打亂」；`ADR-005` 放寬與收緊的不對稱設計。

**為何不細分歸因**：多 agent 的缺陷常源於**交接**而非單一 agent——細分歸因會產生「每個 agent 看起來都沒錯，但結果是錯的」的歸因黑洞。

---

### 2.4 細則 4：token 分帳與 report 聚合格式

**規則**
1. **token 預算為團隊共用**：`token_budget`（SR7）的上限適用於**整個團隊的總和**，不是每個 agent 各一份。
2. **分帳可見**：`report.json` 的 `usage` 區段須列出每個成員的用量，並提供團隊總計。
3. **report 由隊長聚合為單一份**：CI 只讀一份 `.factory/run/report.json`；`changedPaths`／`changedLines`／`requirements` 為**團隊合併結果**。
4. **crosscheck 對象不變**：`factory-crosscheck` 仍以「report vs 實際 git diff」比對——多 agent 不得成為報告失真的藉口。
5. 成員的個別 session log 須保留為 artifact，供事後追查。

**依據**：`ADR-010`「report/judge/token 管線需先重新設計為『隊長聚合報告』」；`docs/04` §5.1（用量為 CI 實測，非 agent 自報）。

**為何團隊共用預算**：若每個 agent 各有上限，總成本隨團隊規模線性膨脹，SR7 形同虛設。

---

### 2.5 細則 5：stop-rules 由隊長繼承並可轉交

**規則**
1. **`factory-stop-rules` 全部八條對每個成員生效**——不因分工而豁免任何一條。
2. **任一成員觸發停手 → 整個團隊停手**。不得「換一個 agent 繼續試」。
3. **隊長負責交還**：停手時由隊長在 Issue 留言、貼 `needs-human`、結束整個團隊。
4. 停手原因須標明**觸發成員**與**觸發條款**，供 `factory-scorer` 統計。
5. **禁止繞道**：成員不得以「這條規則是給別的角色的」為由自行放寬（沿用 SKILL 既有措辭「任何一條觸發即停止，不得自行放寬」）。

**依據**：`factory-stop-rules` SKILL；`docs/02` §6（每個終態都必須明確）。

**為何一人停手全隊停手**：若允許換手重試，等同讓團隊擁有「無限重試」能力——這正是 `docs/02` §6「失敗不自動重試」要防的。

---

## 3. 人類審查永不移除（總括條款）

以上五項細則**不得**被解讀為「多 agent 可以減少人類審查」。明確重申：

- `ADR-005` 的自主性上限（on-the-loop 且限定低風險類別）**不因引入多 agent 而放寬**
- `CODEOWNERS` 的保護範圍不變
- H1–H7 硬性規則不變
- 引入多 agent **不是**進入 Phase 3 的替代路徑

> **多 agent 是執行方式的改變，不是監督層級的改變。** 若有人以「有審查者 agent 了」為由主張放寬人類審查，本節即為駁回依據。

## 4. 引入前的檢查清單

真要引入時，逐條確認：

- [ ] 細則 1：spawn 確認機制已實作，且 CI 無人確認時等同拒絕
- [ ] 細則 1：遞迴 spawn 已被機制阻擋（非僅提示層約定）
- [ ] 細則 2：審查者輸出未進入任何 gate（以 `PipelineInput` 型別保證）
- [ ] 細則 3：團隊樣本與單 agent 樣本分開統計
- [ ] 細則 4：token 為團隊共用上限；report 為單一聚合檔
- [ ] 細則 4：crosscheck 對聚合 report 仍有效
- [ ] 細則 5：任一成員停手即全隊停手，隊長負責交還
- [ ] §3：人類審查範圍未因引入而縮減
- [ ] ADR-010 條件 2：DSH 版本相容 ＋ headless guardrail 實測通過
- [ ] ADR-010 條件 3：確有單 agent 無法勝任的工作項型別（附證據）

## 5. 技術前提（ADR-010 條件 2 的展開）

證據 E 顯示，安全的跨代理人交接需要以下能力。引入前須確認 DSH 具備等價機制，或明確接受其缺席的後果：

| Warp 機制 | 作用 | DSH 等價物 | 缺席的後果 |
|---|---|---|---|
| `ResumePayload`／`SavePoint` | 重建既有會話狀態 | ❓ 未驗證 | 交接後上下文遺失 |
| `fetch_transcript_envelope`／`rehydrate_*` | 下載並重建 transcript | ❓ 未驗證 | 第二個 agent 不知前因 |
| Parent Bridge（共享狀態目錄） | 父子代理人通訊 | ❓ 未驗證 | 無法協調 |
| End-of-Run Snapshots（`snapshot_state.json`） | 環境最終狀態 manifest | 部分：artifacts 上傳 | 無法驗證交接點狀態 |

> **具體風險（fix-bug 案例）**：`docs/07` §2.2 要求 01-test 的紅燈驗證**在同一 agent 沙箱內完成**（寫測試→跑確認紅→實作→跑確認綠）。若拆給兩個無狀態 agent，第二個**沒見過紅燈**，無法確認測試真能捕捉該缺陷——而 `docs/07` §2.1 明列 01-test 置底正是為了「防堵 agent 為了讓測試通過而弱化測試」。**這是靜默失效**：流程看似完成，保護已失效。
