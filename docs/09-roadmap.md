# 09 — 分期路線圖

> **依據**：`00-source-summary.md` §3（三階段路線）、`02-architecture.md` D5（自主性上限）、各文件的未決事項
> **讀者**：決定投資與排程的人
>
> **本文件的立場**：每一期都有明確的**出場條件**與**放棄條件（kill criteria）**。沒有放棄條件的路線圖是願望清單，不是計畫。

## 0. 分期總覽

| 期別 | 名稱 | 對應來源研究 | 核心產出 | 預估 |
|---|---|---|---|---|
| **第 0 期** | 前提就緒與基線 | `00` §3 Phase 1 Step 1 的「前提」 | 非 AI 自動化齊備 + 量測基線 | 2–4 週 |

## 1. 第 0 期：前提就緒與基線

### 為什麼必須有這一期

`00` §3 Phase 1 Step 1 的原文立場非常明確：

> 傳統（非 AI）自動化實踐，例如持續整合（含單元測試自動化）、靜態程式碼分析、自動化生產部署，**應被視為引入 AI 進行更進階使用案例之前的基本前提**。在系統性低效存在時，零散地將 AI 用於臨時性使用案例，**會放大那些低效而非解決它們**。

**跳過這一期的後果是可預測的**：agent 產出大量 PR，但沒有可靠的自動化測試把關，於是全部壓到人工審查，瓶頸瞬間爆炸。這正是 `00` §7「效力轉移而非節省」的教科書案例。

> 使用者已確認採用 **GitHub Actions**（D7）。但**平台就緒不等於前提就緒**——仍須確認目標 repo 實際具備測試與靜態分析的 workflow。

### 工作項

| # | 工作 | 產出 |
|---|---|---|
| 0.1 | 確認/建立 CI：測試自動化 | 綠燈的 Actions workflow |
| 0.2 | 確認/建立靜態分析與 lint | 同上 |
| 0.3 | 確認/建立自動化部署 | 同上 |
| 0.4 | 建立 `main` 分支保護與 CODEOWNERS | `05` §2.2 的設定 |
| 0.5 | **量測基線**（`08` §4） | 填妥 `08` §4.2 的基線記錄表 |
| 0.6 | 執行價值流工作坊（`01` §4） | 更新 `01` §2 的痛點（把假設換成事實） |
| 0.7 | 驗證 DSH headless profile 可執行 | Q02-1/Q04-1 得到答案 |

### 出場條件（全部滿足才可進入第 1 期）

- [ ] 目標 repo 的 CI 可自動執行測試，且**測試涵蓋核心路徑**
- [ ] 靜態分析與 lint 在 PR 上自動執行
- [ ] `main` 受保護，required checks 已設定
- [ ] `08` §4.2 基線表已填妥（樣本 ≥ 20）
- [ ] `01` §2 的痛點已由工作坊實證更新
- [ ] `dsh --profile headless "測試任務"` 在本機可成功執行並回傳 exit 0

### 放棄條件

> 若目標 repo 的測試覆蓋薄弱到**無法信任 CI 綠燈**，且團隊無意補強——**停止整個工廠專案**。
>
> 理由：工廠的安全性完全建立在「CI 綠燈代表沒有明顯破壞」這個假設上。假設不成立時，工廠只是一台高速產生未驗證變更的機器。此時該做的是補測試，不是導入 agent。

## 2. 第 1 期：最窄路徑打通

### 目標

**一條端到端可運作的路徑**，不求覆蓋面。刻意選擇風險最低的任務類型。

### 範圍（刻意極小）

| 項目 | 第 1 期的選擇 | 理由 |
|---|---|---|
| 試點 repo | **1 個**，且為內部工具（非客戶端） | `06` 計分最低，失敗代價最小 |
| 任務類型 | **`agent-add-tests` 一種** | `00` §6 明列的 on-the-loop 類別 |
| 監督層級 | **全部人類審查**（即使計分 0–1） | 第 1 期**不開放自動合併** |
| Backstage | Catalog + 1 個 Template | 不做 TechDocs 與 Scoreboard |

> **第 1 期不開放自動合併**：即使計分允許，也先全部人工審查。理由——尚無 `08` §2.4 的品質數據可證明 agent 可信。信任應由數據建立，而非由設計假設。

### 工作項

| # | 工作 | 依據 |
|---|---|---|
| 1.1 | 建立 GitHub App、設定權限、安裝（**人類手動**） | `02` D6 |
| 1.2 | 建立 factory profile 與 guardrail patch 層 | `04` §2.2–2.3 |
| 1.3 | 撰寫 4 個工廠 skills | `04` §3.3 |
| 1.4 | 撰寫 `factory-run.yml` workflow | `04` §4.1 |
| 1.5 | 撰寫 `06` 計分邏輯與 `risk-paths.yml` | `06` §5 |
| 1.6 | 試點 repo 的 `catalog-info.yaml`（含三軸） | `03` §2.2 |
| 1.7 | Backstage 本機部署 + 1 個 Template | `03` §3, §6 |
| 1.8 | 端到端試跑 ≥ 10 個工作項 | — |

### 出場條件

- [ ] 從 Backstage 觸發 → agent 執行 → stacked PR → 人類審查 → 合併，**全程可運作**
- [ ] `05` §8 的治理檢查清單**逐條通過**
- [ ] 完成 ≥ 10 個工作項，且 `08` §2.3 的執行成功率 ≥ 70%
- [ ] 停手機制**已被實際觸發過至少一次**且行為正確
- [ ] 所有第 1 期相關的未決事項已有答案（Q02-1、Q03-2、Q04-1/2/6、Q07-2）

> **「停手機制已被實際觸發過」是刻意的出場條件**。未經驗證的錯誤處理路徑等同不存在。若十次執行都沒觸發過停手，應**刻意製造一次**來驗證。

### 放棄條件

以下任一成立，**暫停並重新評估**：

- 執行成功率 < 40%（agent 無法勝任最簡單的任務類型）
- 審查 agent 產出的時間 **≥ 人類自己動手的時間**（工廠是負收益）
- Backstage 的維運負擔明顯超過其提供的價值（Q03-6）
  → 此時可考慮**降級方案：拿掉 Backstage，直接用 GitHub Issue 觸發**。架構的 D1 使這個降級成本很低（`02` §6）。

## 3. 第 2 期：擴大與治理

### 目標

從一種任務擴大到多種，從一個 repo 擴大到數個，並補上 `00` §3 Phase 2 要求的平行化與治理。

### 工作項

| # | 工作 | 依據 |
|---|---|---|
| 2.1 | 擴充至 `agent-fix-bug`、`agent-update-deps`、`agent-write-docs` | `03` §3.1 |
| 2.2 | 擴大至 2–3 個 repo（含 1 個較高風險者） | — |
| 2.3 | 驗證 `06` 計分在高風險 repo 的實際行為 | `06` §6 |
| 2.4 | 實作二次判定（PR 建立後重新計分） | `06` §5.3 |
| 2.5 | 接上 OTel 指標後端，自動化 `08` 產出型指標 | `08` §7 |
| 2.6 | 設定 token 中止門檻（此時已有基線） | Q02-5 |
| 2.7 | TechDocs 發佈 + Scoreboard | `03` §4–5 |
| 2.8 | 執行第二次價值流工作坊 | `01` §4.5 |

### 出場條件

- [ ] ≥ 3 種任務類型穩定運作
- [ ] 二次判定機制運作正確（曾成功攔截升級情況）
- [ ] `08` 產出型指標自動化，可對照基線
- [ ] **閒置比較基線下降**，且**缺陷逃逸率未上升**
- [ ] 累積足夠樣本可評估自動合併風險（建議 ≥ 50 個工作項）

> **第 4 條的成對要求呼應 `08` §5.3**：速度指標的改善必須搭配品質指標的持平或改善才算數。只有速度改善而缺陷上升，是把成本推遲到未來，不是改善。

### 放棄條件

- 缺陷逃逸率**顯著高於**基線 → 收緊 `06` 門檻，不進入第 3 期
- 審查佇列深度持續增長 → 投放量超過審查容量（`07` §6.3），應降低投放而非繼續擴大

## 4. 第 3 期：有限自主（受 D5 限制）

### 目標與明確的邊界

依 **D5**，本期**不追求完全自主**。目標僅為：**低風險類別的 on-the-loop 自動合併**。

**明確排除**（`02` §8）：
- ❌ 生產環境自動修復
- ❌ 高風險類別的自主執行
- ❌ 跨組織 agent 生態系
- ❌ vibe coding 式全自主流程

### 進入條件（嚴格，須全部滿足）

- [ ] 第 2 期出場條件全部達成
- [ ] **自動合併候選類別的缺陷逃逸率為 0**，樣本 ≥ 50
- [ ] `06` 計分門檻已經過實務校準（Q06-1）
- [ ] 團隊對 agent 產出品質有共識信任（非個人意見，需問卷或討論記錄）

> **進入條件遠嚴於出場條件是刻意的**。放寬自主性是不可逆的信任讓渡——收回時，團隊往往已經失去了原本的審查習慣（`00` §7 的技能退化）。

### 工作項

| # | 工作 | 依據 |
|---|---|---|
| 3.1 | 開放 `agent-add-tests`、`agent-write-docs` 的自動合併 | `06` §4.2 |
| 3.2 | 建立自動合併的事後抽查機制 | `06` §4（on-loop 定義：例外時介入） |
| 3.3 | 實作 Operate 階段的回饋迴路（異常 → 新 Issue） | `01` §2.6 |
| 3.4 | 成果型指標的季度檢視 | `08` §3 |

### 持續放棄條件

> **任一自動合併類別出現缺陷逃逸，立即收回該類別的自動合併權限**，並回到人類審查。恢復需重新滿足進入條件。
>
> 這是單向棘輪的反向：**放寬需要數據，收緊只需要一次事故。** 這種不對稱是刻意的。

## 5. 跨期的前提與風險

### 5.1 必須由人類完成、不可自動化的事

| 事項 | 期別 |
|---|---|
| 建立 GitHub App 與安裝 | 第 1 期 |
| 決定各服務的三軸風險等級 | 第 1 期起持續 |
| 價值流工作坊與同理心地圖 | 第 0 期、每季 |
| 政策放寬的決定 | 各期 |
| 高風險類別的設計與實作 | 永久（D5） |

### 5.2 最大的三個風險

| 風險 | 徵兆 | 因應 |
|---|---|---|
| **審查成為新瓶頸**（`00` §7 已預告） | 審查佇列深度增長、審查等待時間上升 | `07` 縮小 PR；降低投放量 |
| **信任過早建立** | 一次通過率極高但無缺陷數據佐證 | `08` §2.2 交叉檢核；維持人工審查 |
| **Backstage 維運成本超過價值** | 使用率低、維護耗時 | 第 1 期評估點；可降級為純 GitHub 觸發 |

## 6. 每期都要問的問題

各期結束時，誠實回答：

1. **閒置比下降了嗎？**（`08` §2.1）——若否，改善只是局部的。
2. **缺陷逃逸率上升了嗎？**（`08` §2.4）——若是，速度是借來的。
3. **創新工作佔比上升了嗎？**（`08` §3.1）——若否，省下的時間沒有再投資。
4. **審查還是認真的嗎？**（`07` §6.3）——若否，最重要的安全網已失效。
5. **下一個限制在哪裡？**（`01` §4.5）——限制會移動，上一期的答案已經過期。

> **第 3 題是判定工廠是否值得存在的問題**。前兩題衡量工廠運作得好不好，第 3 題衡量它是否帶來價值。`00` §8 的整節論述就是為了這個區分。
