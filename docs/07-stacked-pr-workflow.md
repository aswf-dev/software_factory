# 07 — Stacked PR 工作流

> **依據**：`02-architecture.md` D3（一個工作項 = 一疊 stacked PR）、`00-source-summary.md` §7（效力轉移而非節省的警示）、`06-human-oversight-policy.md`（合併權限）
> **讀者**：撰寫工廠 skills 的工程師、以及所有審查 agent 產出的人
>
> **查證聲明**：本文件的 `gh stack` 指令與旗標**已由本機安裝的 gh-stack v0.0.2 實測查證**（`gh stack <cmd> --help`）。標註 ✅ 者為實測結果。

## 1. 為什麼是 stacked PR

### 1.1 這是對一個具體警示的回應

`00` §7 的三大警示之一：

> 別只聚焦編碼效率——開發者花更多時間在規劃、設計、架構、測試等非編碼工作。只優化編碼的風險是：**開發期省下的時間，被更大的 code review 待辦積壓抵銷**。這是「轉移」效力而非「節省」效力。

`01` §2.3 的分析也指出：**等待審查者有空，通常是整條價值流最長的閒置段**。

**若 agent 產能提升 5 倍而審查方式不變，結果不是快 5 倍，是審查佇列積壓 5 倍。** 瓶頸只是從 Create 移到 Verify。

### 1.2 stacked PR 如何回應

| 大顆 PR | 一疊小 PR |
|---|---|
| 800 行，涵蓋測試+實作+文件 | 3 顆各 100–300 行，各有單一關注點 |
| 審查者需 1 小時完整脈絡切換 | 每顆 5–15 分鐘可判讀 |
| 審查易流於形式（規模造成疲勞） | 每顆都能實際讀懂 |
| 一處有問題則整體卡住 | 底層先合併，問題只卡該層以上 |
| 衝突範圍大 | 衝突局部化 |

**核心洞見**：審查品質與 PR 大小**非線性負相關**——超過某個規模，審查者就不再逐行讀了，而是憑印象核准。那時的審查是形式上的安全感，比沒有審查更危險，因為它讓人以為已經檢查過。

> **與 `05` §7.1 的關聯**：那裡提到「嚴謹審查」與「提升速度」的張力無法用工具消除，只能靠縮小審查單元緩解。本文件就是那個緩解手段的具體設計。

## 2. 拆分規則

### 2.1 標準序列

一個工作項預設拆為三層，**由底而頂**：

```
trunk (main)
  └── 01-test    測試/契約先行——描述「正確」的定義
        └── 02-impl    實作——使測試通過
              └── 03-docs    文件與註解更新
```

**為何測試在最底層**：

1. 審查者先看到**「正確」的定義**，再看實作，判斷成本大幅降低。
2. 若測試層被否決，實作層不必浪費審查時間。
3. 防堵最危險的失敗模式——**agent 為了讓測試通過而弱化測試**。測試若已在下層被獨立審查並合併，就不能事後偷改。

> 這一點與 `04` §3.3 的 `factory-stop-rules` 第 6 條（「測試無法在不放寬斷言的情況下通過就停手」）互為表裡：一個是提示層規則，一個是流程層結構。

### 2.2 拆分原則

| 原則 | 說明 |
|---|---|
| **單一關注點** | 一顆 PR 只做一件可用一句話描述的事 |
| **可獨立通過 CI** | 每顆 PR 都必須自身綠燈，不可「合併後才會過」 |
| **可獨立審查** | 審查者不需讀上層 PR 才能判斷本層 |
| **拆分建議上限 200–300 行** | 超過則建議再拆；⚠️ 待校準（Q07-1）。**注意**：這是撰寫指引，**非**自動合併門檻——後者為 ≤ 200 行且更嚴格（`06` §4.1） |
| **不可跨風險層級** | 高風險變更**單獨成 PR**，不與低風險混在一起 |

> **最後一條最重要**：若一顆 PR 同時含格式化與授權邏輯變更，`06` 的計分會將整顆判為高風險（正確但低效），且審查者容易在大量格式雜訊中漏看關鍵改動。**風險隔離即審查效率**。

### 2.3 不適用 stacking 的情況

不是所有工作項都該拆疊。以下情況用單一 PR：

- 變更本身 < 100 行且單一關注點（如修正一個 typo）；
- 純機械式全域替換（如相依套件版本更新）——拆開反而增加噪音。

> **判準**：拆分的目的是降低審查成本。若拆分後的總審查成本高於單一 PR，就不該拆。**規則服務目的，不是目的本身。**

## 3. 指令流程（✅ 已實測查證）

### 3.1 建立一疊 PR

> ⚠️ **版本相容（2026-08-18 試點 #2 更正）**：CI 鎖定 gh-stack **v0.1.0**——`gh stack init` **不接受 `--numbered`/`--prefix`**（先前 §3.2 的「實測」實為本機舊版 0.0.2，誤標 v0.1.0）。v0.1.0 的正確用法：**init 直接列出各層分支名**（依序建立、slash 保留）。

```bash
# 1. 初始化 stack（v0.1.0：直接列各層分支名，依序建立）
gh stack init --base "$BASE_BRANCH" \
  "factory/123-01-test" \
  "factory/123-02-impl" \
  "factory/123-03-docs"

# 2. 逐層加入（✅ 實測旗標）
#    -A 暫存所有變更（含未追蹤檔案），-m 提供 commit message
git add tests/
gh stack add -m "test: add failing tests for issue #123" -A

# ... 實作 ...
gh stack add -m "feat: implement fix for issue #123" -A

# ... 文件 ...
gh stack add -m "docs: update usage notes for issue #123" -A

# 3. 一次建立整疊 PR（✅ 實測旗標）
#    --auto 使用自動產生的標題，不互動提示（CI 必需）
gh stack submit --auto
```

> ✅ **實測確認**：`gh stack add` 在「省略 `-m` 但使用 `-A`/`-u`」時會開啟編輯器——**CI 中必須永遠提供 `-m`**，否則會卡住直到 job timeout。這是 agent skill 中必須明寫的細節。

### 3.2 分支命名

採用 `gh stack init --base <trunk> factory/<issue>-<nn>-<layer> ...`（直接列出分支名）：

```
factory/12-01-test
factory/12-02-impl
factory/12-03-docs
```

| 段 | 意義 |
|---|---|
| `factory/` | 標示為工廠產出，便於篩選與設定分支規則 |
| `12` | 對應的 Issue 編號，可追溯 |
| `01`, `02` | 疊序，明示合併順序 |

> ✅ **Q07-2 已更正（2026-08-18，試點 #2 根因調查）**：gh-stack **v0.1.0 不接受 `--numbered`/`--prefix`**——先前「`--prefix "factory/12" --numbered` → `factory/12-01-test`」的實測是在本機舊版 0.0.2 上做的，誤標為 v0.1.0。v0.1.0 用 positional 分支名建立（本機 0.0.2 交叉驗證：`gh stack init -b main "factory/12-01-test" "factory/12-02-impl"` → 依序建立、slash 保留）。疊內各層的語意標籤（`test`/`impl`/`docs`）由 `gh stack add -m` 的訊息推導。

### 3.3 同步與 rebase（✅ 已實測差異）

兩個指令的行為**明確不同**，選錯會造成 CI 卡住：

| 指令 | 行為（✅ 實測 help 文字） | CI 適用性 |
|---|---|---|
| **`gh stack sync`** | fetch → 快進 trunk → 串聯 rebase → **原子性推送**（`--force-with-lease --atomic`）→ 同步 PR 狀態。**偵測到衝突時，將所有分支還原至原始狀態**並建議改用互動式 rebase | ✅ **CI 首選**：非互動、安全、衝突時自動還原 |
| **`gh stack rebase`** | 串聯 rebase；具 `--continue`/`--abort`/`--upstack`/`--downstack` | ⚠️ 衝突時需互動介入；CI 中僅可搭配 `--abort` |

**CI 中的策略**：

```bash
# 優先使用 sync：衝突時它會自行還原，不會留下半完成狀態
if ! gh stack sync; then
  echo "stack sync 失敗（可能為衝突）"
  # 不嘗試互動式 rebase；依停手規則交還人類
  exit 1
fi
```

> ✅ **這是本文件最重要的實測發現**：`sync` 在衝突時「restore all branches to their original state」，這正是自動化所需的交易性語義——**要嘛全成功，要嘛回到原點，不留半成品**。

### 3.4 合併（✅ 實測）

```bash
# 合併指定 PR 及其下方所有 PR（✅ 實測：「Merges the specified PR and all PRs below it」）
gh stack merge <pr-number>
```

**合併順序恆為由底而頂**——這是 stacked PR 的內在約束，`gh stack merge` 已內建此語義。

**工廠的合併規則**（依 `06` §4）：

| 監督層級 | 合併方式 |
|---|---|
| on-loop（0–1 分）且符合 §4.1 全部條件 | agent 可執行 `gh stack merge` |
| 人類審查（2–4 分） | **agent 不得合併**；人類核准後由人類或自動化合併 |
| in-loop（5–6 分） | agent 根本不進入實作階段 |

### 3.5 疊層 PR 的合併流程（2026-08-18 觀察期實測標準化）

> **背景**：gh-stack 建立的疊層 PR 在 GitHub 端受「stacked PR」追蹤——`gh pr merge`（GraphQL）會拒絕：「part of a stack, use the asynchronous merge REST API」；而本 repo **未啟用 async merge API**（`merge-async` 端點 404）。因此合併需先解除疊層關聯。這是平台限制，非流程缺陷。

**人類合併一疊 PR 的標準流程**（每疊由底而頂）：

```bash
# 1. 對最底層 PR：先確認其分支「獨立綠燈」（docs/07 §2.2——測試層不得依賴未合併的 API）
# 2. 若 merge 被「part of a stack」擋住，解除疊層關聯：
gh stack checkout <底層PR編號>     # 匯入該疊
gh stack unstack                    # 刪除 GitHub 端的疊層關聯（分支與 PR 保留）
git checkout main
# 3. 更新分支至最新 main（strict checks 要求同步）：
gh pr update-branch <底層PR編號>
# 4. 合併（squash）：
gh pr merge <底層PR編號> --squash --delete-branch
# 5. 上層 PR 的 base 分支會隨之刪除 → 重建為 main-based（僅該層內容）並開新 PR：
#    git checkout -b <branch> origin/main && <套用該層變更> && push && gh pr create --base main
```

**關鍵注意**：
- **每層必須能獨立綠燈**（2026-08-18 #61 教訓）：測試層不得引用未 export 的 API；若測試需要某個 export，把 export 併入測試層（export 是測試基礎設施），02-impl 只放真實行為變更。
- **上層 base 分支被刪除時**：PR 會關閉——該層內容需重建為 main-based 的新 PR（保留 commit 內容，重開 PR）。
- **strict required checks**：main 每有合併，其餘 PR 變 BEHIND——合併前 `gh pr update-branch`。
- 此流程對人類審查者是**程序性摩擦**，已列入觀察期指標（審查等待時間）；若摩擦持續偏高，考量合併策略調整（如降低疊層層數）。

## 4. 衝突處理與停手規則

### 4.1 停手規則（對應 `04` §3.3）

```
gh stack sync 失敗
      │
      ├─ 第 1 次 ─► 重新 fetch 後再試一次
      └─ 第 2 次 ─► 停手：標記 needs-human，留言說明，結束
```

**為何是「連續兩次」而非更多**：

- 第一次失敗可能是暫時性的（遠端剛好有新 commit）；
- 第二次仍失敗代表存在**真實的語意衝突**，而語意衝突需要理解意圖才能正確解決——這正是 `00` §6 中屬於人類的判斷。

> **明確禁止**：agent **不得**為了通過而使用 `--force` 覆蓋他人變更，也不得刪除衝突的變更。這類「解決」方式會靜默丟失他人的工作。

### 4.2 交還人類時必須提供的資訊

停手時在 Issue 留言中附上（讓人類能接手而非重做，對應 `05` §7.1 措施 4）：

```markdown
### 工廠執行中止

**原因**：`gh stack sync` 連續兩次失敗（疑似語意衝突）

**已完成**：
- `factory/123/01-test`：已建立，PR #456，CI 綠燈
- `factory/123/02-impl`：已建立，PR #457，**衝突於 `src/order.ts`**

**衝突內容**：
<衝突的檔案與區段摘要>

**建議下一步**：人工解決 `src/order.ts` 的衝突後執行 `gh stack rebase --continue`

**執行紀錄**：<Actions run 連結>
```

## 5. PR 描述的要求

每顆 PR 的描述必須包含（對應 `05` §7.1 措施 3——審查者需能驗證推理而非只看結果）：

```markdown
### 這顆 PR 做什麼
<一句話>

### 為什麼這樣做
<設計理由；若有替代方案，說明為何未採用>

### 這一層在疊中的位置
第 2/3 層（下層：#456 測試，上層：#458 文件）

### 審查重點
<明確指出希望審查者特別檢查什麼>

### 相關
Closes #123
```

> **「為什麼這樣做」是必填**。`00` §7 的技能退化警示意味著：審查者若只能看到「改了什麼」而看不到「為何」，就只能驗證語法而非驗證判斷。**agent 必須交代推理，否則人類無從監督。**

## 6. 對審查者的指引

### 6.1 審查一疊 PR 的順序

**由底而頂，逐層審查。** 不要先看最上層。

| 層 | 審查重點 |
|---|---|
| `01-test` | 測試是否真的驗證了驗收條件？斷言是否夠強？**有無為了好過而寫弱測試？** |
| `02-impl` | 實作是否符合已審查的測試？是否有測試未涵蓋的副作用？ |
| `03-docs` | 文件是否與實作一致？ |

### 6.2 審查者的否決權

審查者可在**任一層**否決。否決底層時，上層自動失效——這是 stacking 的效益：**問題在最便宜的時候被攔下**。

### 6.3 不要做橡皮圖章

`05` §7.1 已指出審查嚴謹度與速度的張力。本文件的立場：

> **若你沒有實際讀懂這顆 PR，就不要核准它。**
>
> PR 已被拆到 5–15 分鐘可判讀的規模，這是為了讓認真審查**可行**。若仍覺得沒空細看，代表流量超過團隊的審查容量——**該調整的是工廠的投放量，不是審查的標準**。

這句話值得單獨強調，因為它是整個工廠能否安全運作的關鍵。自動化可以提高產出，但**審查容量是人類的、有限的、不可自動擴張的**。承認這個上限，比假裝它不存在要安全得多。
