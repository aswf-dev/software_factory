# 08 — 指標與 KPI

> **依據**：`00-source-summary.md` §8（成功衡量的原則）、§2（三種時間類型與閒置）、§7（三大警示）、`01-value-stream-map.md` §4（基線量測方法）
> **讀者**：追蹤工廠成效的技術主管與平台團隊
>
> **本文件的核心立場**：指標的用途是**發現瓶頸與偵測副作用**，不是評價個人績效。用途一旦偏離，指標就會被優化給指標看，數據隨即失去診斷價值。

---

## 1. 為什麼需要雙軌指標

`00` §8 的要求很明確：

> 必須超越傳統的**產出型生產力指標**（聚焦交付效率），納入**成果型創造力指標**（聚焦從構想、實驗、策略影響中擷取價值），以確保 AI 省下的時間**再投資於打造新穎且差異化的解法**。

**只看產出型指標的失敗模式**：工廠讓 PR 數量翻倍、lead time 減半，數字很漂亮——但若做的都是低價值的事，或省下的時間只是被更多同類工作填滿，**業務價值毫無增長**。這正是 `00` §7 警示的「效力轉移而非節省」在指標層的表現。

因此本專案採兩軌：

| 軌 | 問的問題 | 特性 |
|---|---|---|
| **產出型** | 工廠**運作得好不好**？ | 易量測、即時、易被操弄 |
| **成果型** | 工廠**帶來價值了嗎**？ | 難量測、滯後、不易操弄 |

> **使用原則**：產出型指標用於**診斷**（找瓶頸），成果型指標用於**判定成敗**（是否值得繼續）。**若產出型全面改善而成果型無變化，代表工廠在高效地做無用功**——這是最需要警覺的訊號。

## 2. 產出型指標

### 2.1 價值流指標（對應 `00` §2）

| 指標 | 定義 | 資料來源 | 為何重要 |
|---|---|---|---|
| **Lead Time** | Issue 建立 → PR 合併的 wall-clock 時間 | GitHub API | 使用者實際感受的速度 |
| **Process Time** | 實際作業時間（不含等待） | Actions run 時長 + 審查耗時 | 與 LT 對比才能算出閒置 |
| **閒置比** | (LT − PT) / LT | 上兩者計算 | ⭐ **`00` §2 的首要改善對象** |
| **各階段停留時間** | 依 Issue 標籤變更時間戳記分段 | GitHub timeline API | 定位瓶頸在哪一階段 |

> **閒置比是本組的核心指標**。`00` §2 的 Figure 3 特別標註「work item is idle」，且 `01` §2.3 判定「等待審查者有空」通常是最長的閒置段。若閒置比未下降，其他改善多半只是局部優化。

### 2.2 審查健康度指標（對應 `00` §7 第二項警示）

**這組指標的存在，是為了偵測「瓶頸從 Create 移到 Verify」這個已被預告的失敗模式。**

| 指標 | 定義 | 警戒訊號 |
|---|---|---|
| **PR 大小分布** | 每顆 PR 的變更行數（中位數與 P90） | P90 持續上升 → 拆分規則失效（`07` §2.2） |
| **審查等待時間** | PR 建立 → 首次審查留言 | 上升 → **審查成為新瓶頸** ⚠️ |
| **審查佇列深度** | 同時處於待審狀態的 PR 數 | 持續增長 → 投放量超過審查容量（`07` §6.3） |
| **一次通過率** | 未經修改即被核准的 PR 比例 | 過低 → agent 品質問題；**過高 → 審查可能流於形式** |

> **「一次通過率過高也是警訊」值得說明**：若 95% 的 agent PR 都一次通過，合理的解釋有二——agent 真的很好，或審查已成橡皮圖章。此時應以缺陷逃逸率（§2.4）交叉驗證。**單一指標無法自證，必須交叉檢核。**

### 2.3 Agent 效能指標

| 指標 | 定義 | 用途 |
|---|---|---|
| **執行成功率** | exit 0 的比例 | agent 可靠性基線（`05` §6.1） |
| **`needs-human` 率** | 停手交還的比例 | 過高 → 任務範圍設定不當 |
| **停手原因分布** | 依 `factory-stop-rules` 各條分類 | 指出最常見的阻塞點 |
| **每工作項成本** | token 消耗（`dsh-token-meter`） | ⭐ 設定中止門檻的依據（Q02-5） |
| **每工作項耗時** | Actions run 時長 | 容量規劃 |

> **注意**：`needs-human` 率**不應**以「越低越好」為目標。設為 KPI 會誘使 agent 在不確定時硬做而非停手——這與 `04` §3.3 的停手規則直接衝突。**這個指標用於診斷，不用於考核。**

### 2.4 品質指標（最重要的安全網）

| 指標 | 定義 | 為何關鍵 |
|---|---|---|
| **缺陷逃逸率** | 合併後才發現的缺陷 / 總合併數 | ⭐ **驗證 `06` 計分門檻是否過鬆** |
| **自動合併缺陷率** | 自動合併的 PR 中事後發現缺陷的比例 | ⭐ **決定 D5 自主性上限能否放寬** |
| **回滾率** | 需回滾的合併比例 | 品質的最終指標 |
| **`needs-human` 後的實際問題率** | 停手是真有問題或誤判 | 校準停手規則的敏感度 |

> **自動合併缺陷率是放寬自主性的唯一依據**。`06` §7.2 規定政策放寬須附實際數據——就是這個數字。若它持續為零且樣本足夠，才有資格討論擴大自動合併範圍；反之則應收緊。

## 3. 成果型指標

`00` §8 與 §1 指出的三個價值驅動，本專案照收為成果型指標：

| 指標 | 量測方式 | 頻率 |
|---|---|---|
| **創新產品與功能數增加** | 新功能（非維護性工作）的交付數量與佔比 | 季 |
| **使用者/客戶滿意度提升** | 既有的使用者回饋管道 | 季 |
| **開發者滿意度提升** | 團隊問卷 | 季 |

### 3.1 關鍵衍生指標：時間的再投資

`00` §8 的核心關切是「省下的時間是否**再投資於打造新穎且差異化的解法**」。因此需要一個直接對應的指標：

| 指標 | 定義 | 判讀 |
|---|---|---|
| **創新工作佔比** | 新功能與探索性工作 / 全部工作 | **上升** → 時間確實再投資 ✅ |
| | | **持平** → 只是做更多同類工作 ⚠️ |
| | | **下降** → 工廠製造了更多維護負擔 ❌ |

> **這是判斷工廠成敗最誠實的單一指標**。若 lead time 減半但創新工作佔比不變，工廠只是讓團隊更快地做同樣的事——那不是 `00` §1 所述的價值，而只是效率的局部改善。

### 3.2 角色導向的指標（`00` §8 的 Vizient 案例）

原文強調：成功擷取價值需要領導者刻意「共同設計」人機關係，**賦權員工實驗個人化、角色導向的指標**，而非強加可能無法反映實際價值創造的生產力度量。

**本專案的做法**：上述團隊層級指標之外，各角色**自行定義**對自己有意義的指標，由 `01` §4.3 的同理心地圖工作坊產出。平台團隊不代為決定。

## 4. 基線的建立

**沒有基線，所有改善宣稱都不可驗證。**

### 4.1 建立時機

**在工廠上線之前**（`09` 第 0 期），依 `01` §4.1 的方法取得至少 20–30 個歷史工作項的數據。

```bash
# 歷史 Issue 的時間戳記
gh issue list --state closed --limit 30 \
  --json number,title,createdAt,closedAt,labels

# 歷史 PR 的規模與時程
gh pr list --state merged --limit 30 \
  --json number,createdAt,mergedAt,additions,deletions,reviews
```

> ✅ **已實測查證**（gh v2.93.0，2026-08-16）：欄位名稱均存在且已實作解析（`src/integration/gh-parse.ts`，16 則測試涵蓋 lead time 與閒置比計算）。

## 5. 指標的反模式（明確禁止）

### 5.1 不得用於個人績效考核

**理由**：一旦指標與考核掛鉤，被量測者就會優化指標而非優化實際成果（Goodhart's Law）。屆時數據失去診斷價值，而診斷正是本文件唯一的目的。

### 5.2 特別危險的指標

| 指標 | 為何危險 |
|---|---|
| **agent 產出的 PR 數量** | 誘使把工作切碎以衝數量，與 `07` 的拆分**目的**背道而馳（拆分是為降低審查成本，不是為衝數字） |
| **agent 自動合併率** | 誘使放寬 `06` 的計分門檻 |
| **`needs-human` 率（作為 KPI）** | 誘使 agent 不確定時硬做而非停手 |
| **程式碼行數** | 與價值無關；AI 時代尤其失真 |

> 這些指標**可作為觀察值**，但**不可作為目標值**。差別在於：觀察值用來理解系統行為，目標值會改變系統行為。

### 5.3 必須成對觀察的指標

單看任一項都會誤導：

| 速度指標 | 必須搭配的品質指標 |
|---|---|
| Lead Time ↓ | 缺陷逃逸率 |
| 自動合併率 ↑ | 自動合併缺陷率 |
| 一次通過率 ↑ | 缺陷逃逸率（防橡皮圖章） |
| PR 數量 ↑ | PR 大小分布（防切碎衝量） |

## 6. 檢視節奏

| 頻率 | 檢視內容 | 對應行動 |
|---|---|---|
| **每週** | 審查佇列深度、`needs-human` 率與原因 | 即時排除阻塞 |
| **每月** | 產出型全組指標 | 定位當前最大瓶頸 |
| **每季** | 成果型指標 + 基線對照 + `01` §4 工作坊 | 解除下一個限制；檢視工廠是否值得繼續 |

> **每季重跑價值流工作坊的理由**（`01` §4.5）：`00` §3 Phase 1 明示限制會移動——只把 AI 用於程式碼生成，瓶頸就下移到 code review。**指標只告訴你數字變了，工作坊才告訴你為什麼。**

## 7. 資料來源與實作

| 指標組 | 來源 | 實作難度 |
|---|---|---|
| 價值流、審查健康度 | GitHub API（Issue/PR timeline） | 低——`gh` CLI 即可 |
| Agent 效能 | Actions run + `dsh-token-meter` → OTel | 中——需接指標後端 |
| 品質 | GitHub Issue（缺陷標籤）+ 回滾紀錄 | 中——需缺陷標記紀律 |
| 成果型 | 問卷 + 工作分類統計 | 高——需人工投入 |

**第一階段的務實做法**：先做**低難度組**（`gh` CLI 腳本 + 每月手動彙整）。不要為了自動化看板而延後工廠上線——`03` §5 已說明 Scoreboard 不阻塞上線。

> **誠實提醒**：成果型指標實作難度最高、最容易被略過，但它們正是判定工廠**是否值得存在**的依據。若只做產出型，就回到了 `00` §8 明確警告的老路。**難做不等於可以不做**。
