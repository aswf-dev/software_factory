# 32 — 工作項規劃指南

> **讀者**：要開一張工作單的人（含非工程背景）。**前提**：你已知道該開哪一張單，或已讀過 [`docs/31`](31-methodology-entry.md) §2 的對照表。
> **用途**：把「想起要做什麼」變成「一張能安全派工的單」。
> **本文件提出的規則**：§4 的**前置工作項**欄位與 **🧭 規劃健檢**是 2026-10 新增的機制；§2、§3 的規則原本就存在（出處逐一標註）。

---

## 0. 規劃 vs 排序：兩件不同的事，只有一件能機械化

`docs/31` §5 說過「規劃是人類專屬」。更精確地說，是**兩件事**：

| | 是什麼 | 誰做 | 工廠的角色 |
|---|---|---|---|
| **規劃** | 這張單做什麼、驗收條件是什麼 | **人類** | 檢查**形式**（可觀察、無空泛詞彙） |
| **排序** | 這張單該不該現在做、要先做完什麼 | **人類** | 檢查你**宣告的前置**寫法是否成立；**不**查它是否已完成 |

**機器無法知道正確順序。** 它不知道你的系統現在缺什麼、哪個模組最痛、哪個團隊有空。任何號稱能自動排程的工具都在猜。

但機器**能**做一件人容易忘的事：**確認你宣告的前置寫得對**（編號存在、不是指自己、沒有無意義的贅字），並在留言中把「這張單在順序上還缺什麼」講出來。這就是 §4。

> **為什麼不讓機器查前置「完成了沒」**：那需要讀取其他 Issue 的狀態（額外的 GitHub 權限），且「前置未完成卻派工」該怎麼處置（擋下？警告？記 `needs-human`？）是需要裁決的政策決定，不是能順手加上的檢查。列為後續工作項。

## 1. 一張合格的工作單長什麼樣

四個必填欄位（`factory-issue-check` 會擋，不合規 `exit 1`）：

| 欄位 | 要求 | 出處 |
|---|---|---|
| **任務類型** | 8 選 1 的下拉選項 | `.github/ISSUE_TEMPLATE/factory-work-item.yml` |
| **需求描述（PRD）** | 目標模組／檔案、做什麼、為什麼、範圍、已知問題（選填不變量） | 同上；`src/factory-draft/prompts.ts` |
| **驗收標準（DoD）** | 三個固定勾選項**全部**要勾（3/3 全勾） | `docs/ADR/009` |
| **目標 repo** | `owner/name`；其他 repo 需另指定 `base_branch` | `README` 接入指引 |

其中「三個固定勾選項」是**對 agent 的固定作業承諾**，對每張單逐字相同——它擋的是「你忘了勾」，不是「你想清楚了」。**真正表達你想清楚的是 PRD 與你自訂的驗收條目。**

## 2. PRD 怎麼寫（核心段落）

```
目標模組 / 檔案：src/scoring/resolve-axis.ts
做什麼（一句話）：修正 changedLines 為 0 時被誤判為 low 的問題
為什麼：上線後發現純文件 PR 被自動合併（應為 medium）
範圍（不碰什麼）：不動評分門檻值，不動 catalog-info.yaml
已知問題：純文件 PR 的 changedLines 過去曾被誤判為 0（若無填無）
不變量：任何情況下 changedLines 不得為負數（選填，若無可省略）
```

| 段落 | 為什麼需要 | 常見寫錯 |
|---|---|---|
| **目標模組 / 檔案** | 工廠據此比對 `risk-paths.yml` 的硬規則，**在花錢前**判斷風險（`docs/18` G5 的姊妹機制） | 只寫「專案某處」→ 無法比對，留言會出現「PRD 未宣告目標檔案」提示 |
| **做什麼** | 一句話。寫不出來通常代表這張單太大 | 寫成三件事 → 該拆成三張單 |
| **為什麼** | 審查者判斷「該不該做」的唯一依據（`docs/07` §5 要求 PR 說明「為什麼」） | 寫成「因為這樣比較好」→ 等於沒說 |
| **範圍（不碰什麼）** | 把「不該動的東西」講明白，避免 agent 擴大範圍（`factory-stop-rules` 第 8 條） | 留空 → agent 只能自己猜界線 |
| **已知問題** | 說明已知雷區、歷史缺口、套件陷阱或環境限制（若無填無）。避免 agent 依照常理推斷而重複踩雷停手（E1 級實證） | 漏填特定環境限制 → agent 在錯誤假設下耗盡 token 或無效停手 |
| **不變量（選填）** | 宣告跨情境不可打破的系統契約或形式化性質（例：INV_MONOTONIC），供 agent 與審查者核對 | 將具體步驟誤寫為不變量 |

> **寫不出目標檔案時**：那正是該先開 `agent-analyze` 的訊號。

## 3. 驗收條件（DoD）怎麼寫

三個固定勾選項不算「你的」驗收條件。請**額外補**這張單專屬、**第三方可驗證**的條目：

| | 範例 |
|---|---|
| ❌ 空泛 | 「確認計分正確」／「優化效能」／「程式碼更完善」（會被提示命中空泛詞彙） |
| ✅ 可驗證 | 「`changedLines=0` 的輸入回傳 `low`」／「`npm run test:unit` 新增 3 則案例全綠」／「回應時間 < 200 ms」 |

**工廠檢查什麼**：只檢查**形式**——每條是否含可觀察結果（命令／輸出／斷言／量化閾值）、是否含空泛詞彙。它**不判斷你的驗收條件對不對**（那是 Validation，屬人類職責；`docs/18` §4 G5）。

**你會被要求沿用編號**：留言會列出 `REQ-1`、`REQ-2`…，請 agent 在 `report.json` 的 `requirements[].id` 沿用。這讓「哪一條驗收條件最常失敗」變成可統計的訊號（`docs/25` §2.3）。**這是 advisory，不影響合規。**

## 4. 前置工作項與 🧭 規劃健檢（新增，2026-10）

### 4.1 欄位

Issue 表單（與 Backstage 表單）最下方有一個**選填**欄位：

```
前置工作項（可留空）：#192, #205
```

- **格式**：`#` 加數字，多個以逗號或空白分隔。**裸數字（`192`）不算**——欄位規範是 `#N`。
- **留空是常態**：多數工作單沒有前置。
- **它是選填**，不是格式要求。填錯不會讓單不合規。

### 4.2 🧭 規劃健檢會說什麼

| 情況 | 留言內容 |
|---|---|
| 欄位留空，且該類型有已知的順序規則 | 「順序上應先開一張 `agent-add-tests`…」等建議 |
| 欄位填了合法編號 | 「已宣告前置 #192、#205。**請確認它們已合併**再派工——本檢查不做 GitHub 查詢，無法代你確認狀態」 |
| 欄位含無法解析的內容 | 「含無法解析的內容：`先做拆分`。請只填 Issue 編號」 |
| 欄位指向本 Issue 自己 | 「指向本 Issue 自己（#42）——這張單將永遠等不到自己完成，請移除」 |

**它不會做的事**：不改變合規判定、不影響計分、不阻止派工、不貼標籤。與「DoD 具體性提示」「風險路徑提示」「REQ 編號」同級，全部是 advisory。

**為什麼刻意做成 advisory**：`docs/21` §4 的類型排序本身仍受 `Q21-4` 未裁決的制約（該節明文寫「本排序在 Q21-4 裁決前不應執行」）。把它做成硬性閘門，等於在裁決前就讓它生效。

### 4.3 「這張單該不該現在做」的四個自問

沿用 `docs/21` §2.0 的進場篩子，改寫成開單者能自己回答的形式：

1. **這件事是「agent 適合做」的嗎**？（對照 `docs/31` §2 對照表；新功能／重構不在其中）
2. **完成了怎麼看出來**？（寫不出可觀察結果 → 這張單還沒想清楚）
3. **風險能不能事先講明**？（目標檔案會不會命中 `risk-paths.yml` 的 H1–H7？會的話預期要人類審查）
4. **有沒有前置**？（該模組有測試嗎？規格來源存在嗎？前置單合併了嗎？）
5. **會不會違反停手規則**？（要改 CI／`CODEOWNERS`／`.dsh/skills/**` 嗎？要改 PBT 測試檔嗎？）

**第 5 題命中就別送**：`factory-issue-check` 會在花錢前擋下（`pbt-outside-audit`、write-spec 欄位），或 agent 會停手交還（第 3、8、11、12 條）。

## 5. 拆分：一張單要拆幾層

一個工作項預設拆**三層**，**由底而頂**（`docs/07` §2.1）：

| 層 | 內容 | 為什麼在這個位置 |
|---|---|---|
| `01-test` | 測試／契約先行——**描述「正確」的定義** | 放最底層，是為了防堵「為了讓測試通過而弱化測試」 |
| `02-impl` | 實作——使測試通過 | 有了正確的定義，實作才有判準 |
| `03-docs` | 文件與註解更新 | 最後，因為它描述已定案的行為 |

- **大小指引**：單層或單 PR ≤ 200 行；整體 200–300 行（`docs/07` §2.2）。這是**撰寫指引，不是閘門**。
- **哪些情況不要 stack**：見 `docs/07` §2.3。
- **`agent-analyze` 只有單層**（報告 PR，不含程式碼變更）。
- **不要跨風險等級混在同一疊**（`docs/07` §2.2）。

## 6. 送出前的檢查清單

```markdown
- [ ] 任務類型選對了（對照 docs/31 §2）
- [ ] PRD 四段都寫了，且「目標模組 / 檔案」是真的路徑
- [ ] 除了三個固定勾選項，我補了至少一條可觀察的驗收條目（無空泛詞彙）
- [ ] 有前置的話，我填了欄位，且**已確認它們已合併**
- [ ] 我不打算改 CI 設定 / CODEOWNERS / .dsh/skills / PBT 測試檔
- [ ] （若是 write-spec）規格來源是人類撰寫或逐條確認的，不是 agent 依程式碼生成的
```

送出後**先讀留言的提示卡再決定要不要 dispatch**。留言是免費的；派工要花 token。

## 7. 已知邊界與後續

| 邊界 | 現況 |

| 規劃健檢**不查**前置 Issue 實際狀態 | 需 GitHub 權限與政策裁決，列後續工作項 |
| 就緒度 → 允許類型**無機械強制** | `docs/29` §5 自承；由開單者自律、審查者把關 |
| 沒有「審查者引導」 | 本期未納入；先用本文件降低流入審查的壞單 |
| 新功能／重構**無對應類型** | `docs/29` §3.4 已知缺口 |
