# 01 — 軟體交付價值流地圖

> **依據**：`00-source-summary.md` §2（價值流六階段）、§3 Phase 1（解除瓶頸）、§3 Phase 2 Step 2（消除與保留）
> **讀者**：規劃工廠範圍的人；本文件決定「哪些階段交給 agent、哪些消除、哪些堅持人工」

---

## 1. 本文件要回答的問題

來源研究的 Phase 1 Step 1 要求：**先映射完整的軟體交付價值流，再決定 AI 用在哪裡**。原文的核心警告是——在系統性低效存在時零散導入 AI，會放大低效而非解決它（`00` §3 Phase 1）。

因此本文件先建立地圖，`02-architecture.md` 才據以設計系統。順序不可顛倒。

### 1.1 分析單位

- **工作項（Work Item）**：從 Request 到 Delivery 的一個可獨立交付的變更。本專案中等同一個 GitHub Issue。
- **Lead Time**：Request 到 Delivery 的總經過時間（wall-clock），**包含等待**。
- **Process Time**：實際作業時間，不含等待。

> **關鍵區分**：Lead Time − Process Time = 閒置時間。來源研究 Figure 3 特別標註「work item is idle」，本專案把閒置視為首要改善對象。

### 1.2 時間分類法（沿用 `00` §2）

| 代號 | 類型 | 處置原則 |
|---|---|---|
| **VA** | Value-Adding：真正產生價值 | 保留；可用 AI 加速 |
| **NNVA** | Necessary Non-Value-Adding：不加值但必要 | 優化、自動化 |
| **UNVA** | Unnecessary Non-Value-Adding：純浪費 | **消除** |
| **IDLE** | 等待、排隊、閒置 | **消除或平行化** |

## 2. 現況地圖：六階段逐一分析

> **重要限制**：以下各階段的「典型痛點」是基於小團隊常見型態的**假設性起點**，用於啟動討論，**不是**對你團隊的實測。實際數據必須透過 §4 的工作坊取得。所有標註 ⚠️ 者為待驗證假設。

### 2.1 Plan（規劃）

| 項目 | 內容 |
|---|---|
| **輸入** | 業務需求、使用者回饋、事故報告、技術債清單 |
| **輸出** | 具備驗收條件的工作項（GitHub Issue） |
| **主要角色** | 產品負責人（PO）、架構師、開發者 |

| 活動 | 時間類型 | 典型痛點 ⚠️ | 處置判定 |
|---|---|---|---|
| 需求釐清與構想發想 | VA | 需求描述模糊，開發者反覆回問 | **保留人工**（agent 輔助產草稿） |
| 撰寫使用者故事與驗收條件 | VA | 驗收條件缺漏，導致 Verify 階段爭議 | **保留人工 + agent 輔助** |
| 技術可行性調查 | VA | 資訊分散，重複調查 | **自動化**（agent 做背景研究） |
| 工作項拆解與估算 | NNVA | 拆解粒度不一致 | **自動化**（agent 依規則拆） |
| 待辦排序會議 | NNVA | 會議時間長、決策未記錄 | 優化（縮短、決策落檔） |
| 等待 PO 有空釐清 | **IDLE** | 工作項卡在「待釐清」數日 | **消除**（非同步澄清機制） |

**階段判定**：**保留人工主導，agent 輔助**。
理由：`00` §6 明列「產品管理、功能優先排序、理解複雜使用者需求、軟體架構」屬 human-in-the-loop；且 `00` §7 警示技能退化——規劃是核心判斷力所在，不可外包。

**agent 在此階段的合法職責**：產生規格草稿、蒐集既有相似實作、標示缺漏的驗收條件、依模板檢查 Issue 完整性。**不得**自行決定要做什麼或優先順序。

---

### 2.2 Create（建構）

| 項目 | 內容 |
|---|---|
| **輸入** | 具備驗收條件的工作項 |
| **輸出** | 一疊 stacked PR，全部 CI 檢查通過 |
| **主要角色** | 開發者（轉為「數位指揮家」）、DSH agent |

| 活動 | 時間類型 | 典型痛點 ⚠️ | 處置判定 |
|---|---|---|---|
| 理解既有程式碼脈絡 | VA | 新人或跨模組時耗時最長 | **自動化**（agent 擅長） |
| 撰寫實作程式碼 | VA | — | **自動化** |
| 撰寫測試 | VA | 常被壓縮或省略 | **自動化**（且先於實作，見 `07`） |
| 撰寫/更新文件 | NNVA | 經常遺漏，文件與程式碼漂移 | **自動化** |
| 建立開發/測試環境 | NNVA | 開票、等待、環境不一致 | **消除**（容器化 + 自助） |
| 等待環境撥配 | **IDLE** | 開票後等待數小時至數日 | **消除** |
| 本機重複執行 lint/test 迴圈 | NNVA | 內部迴圈慢則心流中斷 | 優化（快速回饋） |

**階段判定**：**自動化**（agent 主責，人類審查產出）。
理由：`00` §3 Phase 2 Step 1——agentic 工具已從 code assistant 升級為 feature builder。這是工廠自動化程度最高的階段。

**⚠️ 陷阱警告**：`00` §7 明示——只優化本階段會讓瓶頸下移到 Verify 的 code review。**本階段的產能提升必須同步搭配 `07-stacked-pr-workflow.md` 的審查單元縮小策略**，否則只是把積壓從開發轉移到審查。

---

### 2.3 Verify（驗證）

| 項目 | 內容 |
|---|---|
| **輸入** | stacked PR |
| **輸出** | 通過審查與品質閘門、可合併的變更 |
| **主要角色** | 審查者、CI、安全工具、DSH agent（自審） |

| 活動 | 時間類型 | 典型痛點 ⚠️ | 處置判定 |
|---|---|---|---|
| 自動化測試執行 | NNVA | CI 慢則回饋延遲 | **自動化**（已是前提，見下方註） |
| 靜態分析與安全掃描 | NNVA | 誤報多導致被忽略 | **自動化** |
| 人類 code review | VA | **本階段最大瓶頸** | **分級人工**（依 `06` 判定） |
| agent 自我審查 | NNVA | — | **自動化**（提交前先自審） |
| 等待審查者有空 | **IDLE** | **通常是整條價值流最長的閒置段** | **消除/大幅縮短** |
| 修正審查意見後重跑 | NNVA | 來回多輪 | 優化（一次到位率） |
| 手動回歸測試 | UNVA | 耗時且易漏 | **消除** |

**階段判定**：**自動化 + 分級人工**。
理由：`00` §3 Phase 2 Step 1 明示現階段技術成熟度無法保證一致性、準確性與可預測性，故人類監督為強制；但監督強度依 `06` 的三軸計分決定。

> **前提條件**：`00` §3 Phase 1 Step 1 明確要求——CI、單元測試自動化、靜態程式碼分析、自動化生產部署，是**引入 AI 前的基本前提**，不是 AI 的成果。若團隊尚未具備，應先補齊這些非 AI 自動化，再談 agent 化。這是 `09-roadmap.md` 第 0 期的內容。

---

### 2.4 Release（發布）

| 項目 | 內容 |
|---|---|
| **輸入** | 已核准的 PR 疊 |
| **輸出** | 已合併並部署的變更 |
| **主要角色** | GitHub Actions、發布負責人 |

| 活動 | 時間類型 | 典型痛點 ⚠️ | 處置判定 |
|---|---|---|---|
| 合併 PR（依疊序：底→頂） | NNVA | 疊中衝突需重排 | **自動化** |
| 建置與打包 | NNVA | — | **自動化** |
| 部署至各環境 | NNVA | — | **自動化** |
| 例行性人工核准關卡 | UNVA | 核准者只是按鈕，未實質審查 | **消除**（詳見 §3） |
| 等待發布時窗 | **IDLE** | 批次發布造成積壓 | 優化（小批量、持續交付） |
| 發布後手動驗證 | NNVA | — | **自動化**（冒煙測試） |

**階段判定**：**自動化**。
合併順序必須由 stack 底部往頂部，規則見 `07-stacked-pr-workflow.md`。

---

### 2.5 Configure（設定）

| 項目 | 內容 |
|---|---|
| **輸入** | 已部署的變更、環境需求 |
| **輸出** | 正確且一致的執行環境設定 |
| **主要角色** | 平台工程師、SRE、agent |

| 活動 | 時間類型 | 典型痛點 ⚠️ | 處置判定 |
|---|---|---|---|
| 應用設定變更 | NNVA | 手動改動未落檔 | **自動化**（低風險）/ 人工（高風險） |
| 基礎設施異動（IaC） | NNVA | — | **自動化**（低風險） |
| 設定漂移偵測與修正 | NNVA | 漂移長期未發現 | **自動化偵測**、修正依風險分級 |
| 密鑰與憑證輪替 | NNVA | 易遺漏 | **自動化**（但憑證本身不進 agent context，見 `05`） |

**階段判定**：**低風險自動化、高風險人工**。
理由：`00` §6 把「設定變更」列為 human-on-the-loop 範例，但**涉及授權邏輯或敏感資料的設定屬 human-in-the-loop**。分界由 `06` 的計分規則判定，不由執行者自行認定。

---

### 2.6 Operate（維運）

| 項目 | 內容 |
|---|---|
| **輸入** | 執行中的系統 |
| **輸出** | 可觀測性資料、事故、回饋（成為新工作項） |
| **主要角色** | SRE、值班人員、觀測工具 |

| 活動 | 時間類型 | 典型痛點 ⚠️ | 處置判定 |
|---|---|---|---|
| 監控與告警 | NNVA | 告警噪音高 | **自動化** |
| 事故偵測與分類 | NNVA | — | **自動化偵測** |
| 根因分析 | VA | 耗時 | agent 輔助分析（**不自動修復**） |
| 事故修復 | VA | — | **本期保留人工** |
| 事後檢討 | VA | 常被省略 | agent 輔助整理，結論由人定 |
| 手抄式狀態回報 | UNVA | 佔用工程時間 | **消除**（自動產生） |

**階段判定**：**本期僅監測與輔助分析，不自動修復**。
理由：`00` §3 Phase 3 提及 Augmented SRE 與自癒系統是方向（預測 2029 年 60% SRE 將卸載例行事故工作），但那屬 Phase 3 成熟階段。本專案的自主性上限已由架構決策 **D5** 設定為「on-the-loop 且限定低風險類別」，生產環境自動修復不在此範圍。

**回饋迴路**：Operate 階段發現的問題，一律回流為 Plan 階段的新工作項（GitHub Issue）。這構成 `00` §3 Phase 3 Step 1 所稱的「自我改善迴圈」的最小可行版本。

## 3. 消除清單（呼應 `00` §3 Phase 2 Step 2）

來源研究要求：**辨識該消除的步驟，而非優化它們**；方法是反覆追問「這個流程為何存在」，確實需要存在才談優化。

以下每項都經過此追問：

| # | 待消除步驟 | 為何存在？ | 是否仍需存在？ | 處置 |
|---|---|---|---|---|
| E1 | **手動開票申請開發/測試環境** | 環境稀缺且需人工撥配 | ❌ 容器化後環境不再稀缺 | **消除**：自助式、以程式碼定義、用完即棄 |
| E2 | **例行性人工核准關卡** | 歷史上作為品質防線 | ❌ 已被自動化檢查覆蓋者純屬形式 | **消除**：僅保留 `06` 判定需要的核准；其餘改為自動化 required checks |
| E3 | **手動回歸測試** | 自動化測試不足時的補償 | ❌ 應改為補足自動化測試 | **消除**：轉為自動化測試套件 |
| E4 | **手抄式狀態回報** | 管理層需要可見度 | ⚠️ 需求正當，但手抄方式不必要 | **消除手抄**：改由系統自動產生（見 `08`） |
| E5 | **等待審查者有空的閒置** | 審查需要人類判斷 | ⚠️ 審查需保留，等待不需要 | **消除等待**：縮小 PR 至可即時審查、非同步化 |
| E6 | **重複的環境設定文件與實際設定不一致** | 文件手動維護 | ❌ | **消除**：設定即文件（IaC 為唯一事實來源） |

### 3.1 必須保留的不變量（`00` §3 Phase 2 Step 2）

原文明示以下人類要素必須保留，本專案照收：

| # | 保留項目 | 理由 |
|---|---|---|
| K1 | **使用者同理心** | 無法自動化；理解真實使用者需求是產品價值來源 |
| K2 | **有效的變革管理** | 創新步調必須配合使用者能吸收變革的步調 |
| K3 | **對 agent 產出的最終責任歸屬** | `00` §3 Phase 2——人類是「數位指揮家」，須對產出負責 |
| K4 | **高風險類別的人工判斷** | `00` §6、§7——避免技能退化與風險失控 |

## 4. 如何取得真實數據：瓶頸識別工作坊

§2 的痛點是假設；本節是把假設換成事實的方法。**建議在動工實作前執行一次。**

### 4.1 準備（30 分鐘）

從 GitHub 匯出最近 20–30 個已完成工作項的時間戳記。可用的查詢起點：

```bash
# 取得最近已關閉的 issue 及其時間戳記（需在目標 repo 內執行）
gh issue list --state closed --limit 30 \
  --json number,title,createdAt,closedAt,labels

# 取得 PR 的建立、首次審查、合併時間
gh pr list --state merged --limit 30 \
  --json number,createdAt,mergedAt,reviews,additions,deletions
```

> ⚠️ 上述指令的 JSON 欄位名稱以 `gh` v2.93.0 為準，實際執行時請以 `gh pr list --json` 不帶值的輸出確認可用欄位。

### 4.2 繪製（60 分鐘，全角色參與）

依 `00` §3 Phase 1 Step 2，**參與者不限開發者**，應包含 PO、UX、平台、安全、品質等角色。

逐階段填寫下表（每階段一列）：

| 階段 | 平均 Process Time | 平均 Lead Time | 閒置比 = (LT−PT)/LT | 最大痛點 | 時間類型 |
|---|---|---|---|---|---|
| Plan | | | | | |
| Create | | | | | |
| Verify | | | | | |
| Release | | | | | |
| Configure | | | | | |
| Operate | | | | | |

### 4.3 角色同理心地圖（30 分鐘）

依 `00` §3 Phase 1 Step 2 的 Vizient 案例，對每個角色追問三個問題：

1. AI 將如何影響**我的工作**？
2. AI 將如何影響**我的責任與擁有權**？
3. AI 將如何影響**我的工作時程**？

> 原文強調：擷取 GenAI 價值需要行為改變，因此必須理解員工如何看待自己的工作與身分認同。這不是形式問卷，答案會直接影響導入阻力。

### 4.4 判定（30 分鐘）

1. 找出**閒置比最高**的階段 → 這是當前最大限制。
2. 對該階段的每項活動判定「消除 / 自動化 / 保留人工」。
3. 檢查：所選解法是 AI 還是傳統自動化？
   > `00` §3 Phase 1 的 CBRE 案例警示——先問「善用既有工具是否更可行」，別預設答案是 AI。
4. 只解除**一個**限制，然後重測。

### 4.5 迭代原則

限制會**移動**。`00` §3 Phase 1 明示：只把 AI 用於程式碼生成，瓶頸就會下移到 code review。

因此本工作坊不是一次性活動，而是每季重跑一次的例行作業。每次只解除當前最大的一個限制。

## 5. 本文件的結論輸出

供 `02-architecture.md` 直接引用的階段處置判定：

| 階段 | 處置 | agent 自主程度 | 人類角色 |
|---|---|---|---|
| **Plan** | 保留人工主導 | 輔助（產草稿、查資料） | 決策者 |
| **Create** | 自動化 | 主責 | 指揮與審查 |
| **Verify** | 自動化 + 分級人工 | 自審 + 提供佐證 | 依 `06` 分級審查 |
| **Release** | 自動化 | 主責（依疊序合併） | 例外處理 |
| **Configure** | 低風險自動化 / 高風險人工 | 依 `06` 分級 | 高風險主責 |
| **Operate** | 僅監測與輔助分析 | 分析輔助，**不自動修復** | 修復主責 |
