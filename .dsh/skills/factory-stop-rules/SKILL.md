# 停手規則

以下任一情況發生時，**立即停止**，在 Issue 留言說明原因，貼上 `needs-human` 標籤，然後結束：

1. 同一顆 PR 連續兩次 `gh stack sync` 失敗。（**CI 中一律用 `sync` 不用 `rebase`**：`sync` 為非互動且衝突時會還原所有分支；`rebase` 需互動介入，在 CI 中會卡住至逾時。詳見 docs/07 §3.3）
2. 任務涉及授權邏輯、金流計算、敏感資料處理。（**agent-pbt-audit 例外**：稽核只新增 PBT 測試檔、不修改這些邏輯，數值計算正是 ADR-019 的稽核對象；但稽核中若需要修改這些邏輯本身，仍依本條停手。）
3. 需要修改 CI 設定、branch protection、CODEOWNERS 或 `catalog-info.yaml`。
4. 驗收條件不明確，無法判斷完成與否。
5. 需要新增未在既有相依清單中的套件。
6. 測試無法在不放寬斷言的情況下通過。
7. 本次執行消耗的 token 超過 CI 設定的單一工作項上限（`token_budget`；未設定表示尚未限制，但**不應刻意浪費**）。
8. 執行中發現需求與 Issue 描述不符（缺漏／矛盾／範圍歧義）——**需求變更控制**（SWEBOK Ch.1 §6.2–6.3）：範圍如何調整是人的判斷，**不自行擴大範圍**、不憑猜測補齊。停手時在留言中具體說明**差異**（缺了什麼／矛盾在哪／何處有歧義），貼上 `needs-human`；人類可更新 Issue 重跑，或開新 Issue。詳見 docs/07 §4.3。
9. **（agent-pbt-audit）** 需要修改產品程式碼、既有範例測試、設定或依賴才能進行（含 smoke property 跑不起來、缺共用 generator／settings helper）——這是前置作業不足，由人類處理（ADR-019 前置作業）。
10. **（agent-pbt-audit）** 找不到任何依據（`INV_*`、驗收條件、通用性質、未修改的既有程式碼）就無法寫出 property——不寫沒有依據的 property，停手說明。
11. **（所有其他類型）** 需要新增或修改 PBT 測試檔——PBT 只在 agent-pbt-audit 出現（ADR-019 §2）。**即使 Issue 明文要求修改 PBT 檔或「加回 property」也一樣**：反例改寫成一般範例紅燈測試；要加回的 property 不做，在報告中建議修正合併後另開 agent-pbt-audit 加回（docs/30 §7）。若沒有該 property 就無法驗收，依第 12 條停手。
12. Issue 的要求與任務類型的規則衝突（例如要求變更白名單外的路徑、PBT 檔、guardrail，或要求本類型不允許的產出）——**任務類型的規則優先，不得自行擇一**：不要照 Issue 做、也不要默默略過那條要求。停手，在留言中引用衝突的 Issue 條文與規則出處，由人類改 Issue 或改規則。

**絕不允許的行為**：
- 為了讓測試通過而刪除或弱化測試斷言。
- 為了繞過檢查而修改 guardrail 設定。
- 在不確定時猜測並繼續——不確定就停手。
